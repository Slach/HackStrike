# AGENTS.md — правила работы в репозитории HackStrike

Прочитай `docs/game-design.md` ПЕРЕД любой задачей по фичам — это источник
истины. Если реализация расходится с докой — либо почини код, либо спроси
владельца; молча расходиться нельзя. Изменения протокола/механик — сначала в
`docs/game-design.md` (§9.2 протокол, §11 журнал решений), потом в код.

## Проект

Браузерная командная FPS с классом хакера (мини-ОС на кибердеке, воздействие
на физический мир). Схема: `browser → nginx(/ws, /api) → zrok → Go-сервер`.

## Раскладка

```
server/          Go-сервер: authoritative-симуляция, тик 30 Гц, одна комната-горутина
  main.go        каркас: WS, комната, тик, healthcheck-режим
client/          TypeScript + Vite + Babylon.js
  src/main.ts    сцена/рендер
  src/net.ts     WS-клиент, реконнект
  nginx.conf     раздача статики + прокси /ws и /api на game-server:8080
docs/
  game-design.md ГДД + wire protocol + roadmap (главный документ)
  research/      зафиксированные research-отчёты (стек, референсы)
```

## Команды

```bash
# сервер: проверка (обязательно перед отчётом о завершении задачи)
cd server && go vet ./... && go test ./... && go build -o /tmp/game-server-check .

# клиент: typecheck + сборка (обязательно)
cd client && npm run build

# полная интеграция (запускает владелец или по его просьбе):
docker compose up -d --build game-client game-server

# локальная разработка без docker:
cd server && go run .                      # :8080
cd client && npm run dev                   # :5173, /ws и /api проксируются
```

## Архитектурные инварианты (нарушать нельзя)

1. **Сервер — единственный источник истины**: позиции, HP, урон, владение
   устройствами, счёт — только сервер. Клиент никогда не решает «убил».
2. **Состояние комнаты трогает только горутина комнаты** (паттерн в
   `server/main.go`): никаких mutex на игровом состоянии, обмен — каналы
   `join/leave/inputs`. Горутина записи на клиента с `WriteDeadline`,
   drop-политика при переполнении send-канала.
3. **Тик фиксированный 30 Гц**, dt = 1/30; вся симуляция — дискретные шаги.
4. **Клиентская сторона**: интерполяция снапшотов (~100 мс в прошлом);
   client-side prediction движения не делаем в MVP.
5. **Wire protocol** — JSON, дискриминатор `"t"` (см. ГДД §9.2). Новые
   сообщения сначала в доку. Бинарный формат — потом, не сейчас.
6. **Карта — данные**: `server/map/map1.json` (go:embed), раздаётся через
   `GET /api/map`; клиент геометрию не хардкодит.
7. **UI-оверлеи — DOM** (HUD, hacker view), не Babylon GUI; рендер-канвас — Babylon.

## Стиль кода

- Go: идиоматичный, без преждевременных абстракций; комментарии — почему, а
  не что; логгирование через `log.Printf` с префиксом подсистемы (`room:`, `map:`).
- TypeScript: strict, без `any` (кроме парсинга протокола — там мапперы);
  Babylon-импорты точечные (`@babylonjs/core/...`), не корневые.
- Протокол: Go-структуры с json-тегами; на клиенте — типы сообщений в `net.ts`.

## Процесс

- **Один объект уровня за итерацию** (правило ГДД §7), с последующей проверкой сборки.
- Перед задачей: перечитай свой участок + ГДД. После: прогони проверки из
  «Команды» и приложи вывод в отчёт.
- Не трогать: `docker-compose.yaml` (только по просьбе владельца), `.env`,
  docs/research (исторические).
- Коммитов без запроса не делать.
- Балансовые числа (HP/урон/скорости) — из ГДД §3; менять можно только через ГДД.
