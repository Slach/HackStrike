# HackStrike — Game Design Document

> Статус: v1.0, зафиксировано 2026-11-14 по итогам дизайн-сессии с автором.
> Документ — источник истины для реализации. Изменения — только через новые
> решения автора (фиксировать в «Журнале решений» в конце).

## 1. Концепция

Браузерная сессионная командная FPS-игра, где **хакер — отдельный класс с
настоящей мини-ОС**. В отличие от Dystopia (3D-киберпространство) здесь
hacker view — **системная симуляция сети**: у каждого кибер-устройства своё
«железо» (CPU/NPU/RAM/NET), программы — это процессы с очередями, а взлом
воздействует на физический мир через контроллеры. ДНК: Uplink / Quadrilateral
Cowboy поверх аренa-шутера.

**Формула:** `(арена-шутер на фраги) + (симулятор сети в реальном времени) + (физические ловушки как гейты)`.

Ключевые отличия от референсов:
- никаких аватаров в киберпространстве — PvP хакеров это **дуэль процессами** (trojan vs antivirus, firewall vs portscan);
- сеть — **геометрия карты** (кабели — несекционируемые линии топологии);
- данные — **лут-рецепты**: чертёж замка + compiler = эксплойт (в полной версии).

## 3. Боевой слой (meatspace)

### 3.1. Классы (v0-баланс, править по плейтестам)

| Класс | Оружие | HP | Скорость | Особенности |
|---|---|---|---|---|
| Снайпер | Bolt-винтовка (hitscan, авто-зум ×1.5) | 100 | 5.5 м/с | ваншот всех, кроме heavy (2 выстрела); стреляет только в зуме |
| Автоматчик | AR, полный авто | 125 | **6.5 м/с (самый быстрый)** | универсал |
| Heavygun | Minigun, раскрутка 0.5 с | 200 | 4.5 м/с | танк, медленный |
| Хакер | Пистолет (полуавто) | 100 | 6.0 м/с | дека у терминала |

TTK ориентир: **~1.5–2 с** при полном контакте (правка 2026-11-14 после плейтеста: автоогонь + магнитизм дают почти 100% попаданий, прежние 0.5–1 с ощущались «одним выстрелом»). Оружие v1-числа (сервер валидирует скорострельность):

при потере HP, HP-бар над игроками. Респаун — кнопка (крупная) или SPACE.

### 3.2. Управление и автоогонь (вариант B)

- WASD — движение (относительно взгляда), мышь/тачпад — mouse look (pointer lock).
- **Автоогонь**: оружие стреляет само, когда курсор на цели — без клика.
  Целиться и вести цель должен сам игрок. **Мягкий bullet magnetism**: сервер
  засчитывает попадание, если цель в конусе ~2° от заявленного направления и
  есть LOS. Доворачиваются пули, а не прицел.
- Space — интеракция (двери, терминалы, сейфы). Отдельного прыжка в MVP нет
  (этажи — лестницы с autostep 0.55 м).
- Оружие фиксировано по классу (M2-2: нож хакера удалён — melee с конусом
  наведения оказался неиграбельным; позже удалено и перерубание кабелей
  целиком — см. следующую запись).
- Инверсия вертикали мыши — опциональная настройка на join-экране (клиентская,
  localStorage, `hs.invertY`); на протокол не влияет.
- Переключение оружия — потом (хакеру: пистолет доступен только offline от деки).

### 3.3. Раунд, респаун, победа

- Матч: первая команда до **50 фрагов** или **10 минут** (по счёту на момент
  конца). M5 добавляет третье условие — **извлечение содержимого физического
  сейфа** = мгновенная победа (гонка путей, §16.0).
- Респаун: индивидуальный, **5 с**, на своей базе, класс можно сменить.
- Friendly fire ON (урон и ловушки бьют своих).
- Носитель сейфа: ×0.5 скорости; при смерти сейф падает на землю.

## 4. Миникарта и информация

- Видно: живые союзники (их FOV), захваченные командой камеры/датчики.
- Выстрел врага → стрелка-пеленг на 2 с.
- Кибер-карта (в hacker view): только устройства, обнаруженные своим portscan.
- Общая команда-vision считается на сервере.

## 5. Кибер-слой (hacker view)

### 5.1. Модель устройства

Каждый кибер-объект (включая деку хакера) — хост с характеристиками:

| Ресурс | Ед. | Роль |
|---|---|---|
| CPU | TFLOPS | обычные программы; скорость = доля CPU у процесса |
| NPU | PFLOPS | AI-задачи: нетривиальный поиск, подбор паролей «по словарю», анализ |
| MEM | МБ | память хоста: в ней живут данные (M5) и контекст программ; ограничивает кол-во одновременно запущенных программ; смерть хакера стирает MEM его деки (решение владельца 2026-11-16: PMEM удалён как сущность) |
| NET | МБ/с на интерфейс | проводные/беспроводные каналы; скорость сканов и cp зависит от узкого места маршрута |
| UI | — | у каждого устройства свой: камера = картинка + действия, дека = терминал + HUD-графики загрузки CPU/NPU/RAM/NET |
| CONTROLLERS | — | воздействия на физический мир (выключатели, приводы) |

**Планировщик: честные очереди.** Программы делят CPU/NPU тайм-слайсами:
запустил 5 сканов — каждый идёт в 5 раз медленнее. Загрузка видна на графиках
деки — графики сами становятся геймплеем (перегрузил хост — всё тормозит).
Сервер считает это дёшево (дискретные доли производительности, без потоков).

### 5.2. Программы (v0-список)

Хакерские:
- `portscan` — обнаружение устройств и портов; скорость = NET (узкое место маршрута) × ширина охвата;
- `vulnscan` — перебор уязвимостей через CPU/NPU, включая подбор паролей (мощный NPU = уточнение по словарю вместо тупого брутфорса);
- `trojan` — RCE: запуск своих программ на чужом хосте. Уровни: **userland → kernel → firmware** (kernel = скрыт от обычного ps, firmware = переживает перезагрузку/антивирус дольше). В MVP только userland;
- `watcher` — триггеры на события сети («другой хакер вошёл в устройство»); после смерти хакера триггеры гаснут, но **переподключаются быстро**;
- `crypt/decrypt` — шифрование/расшифровка данных, скорость = CPU/NPU от объёма;
- `firewall` — фильтрует доступ по NET-интерфейсам: режет ТРАФФИК ЧЕРЕЗ
  устройство — сетевая сегментация (M3-срез — §13.5);
- `antivirus` — мешает установке trojan, может быть пробит (гонка версий).

Обычные:
- `cp` (подкоманда `data cp`) — копирование данных между устройствами
  (источник хранит свой экземпляр): приёмнику нужен свободный MEM,
  скорость = узкое место маршрута с учётом конкурентных трансферов (M5
  §16);
- `mv` (подкоманда `data mv`) — перенос данных (item покидает источник,
  §16.2);
- `data analyzer` — извлечение смысла из данных (NPU);
- `compiler` — **отложено**: в видении автора это инструмент NPU для создания
  новых программ из данных (например, чертёж замка → эксплойт контроллера).

### 5.3. Данные как лут

- `data` — не программа, а **данные**: пароли, чертежи замков, документы.
- Рецепт M5 (§16): `NETSAFE/SRV1 → data cp → decrypt → код` (двери d3 /
  физического сейфа) → ввод на месте.
- Полная версия: чертёж + `compiler` (NPU) = кастомный эксплойт/ключ.
- Данные лежат в MEM хоста; смерть хакера стирает MEM его деки (копии на
  сетевых хостах остаются — их может перехватить враг, §16.1).

### 5.4. Hacker view UX

- Вход: только у **терминала** или в радиусе **радио-точки** (провод — мгновенно, радио — теряет скорость NET).
- Выход: **CTRL+ALT+DEL** (win/linux) / **CMD+ALT+DEL** (macOS). Тело стоит у терминала беззащитное.
- Интерфейс — **тайловый оконный менеджер**:
  - F1 = UI своей деки (терминал, графики CPU/NPU/MEM/NET, запущенные
    программы, инвентарь данных в MEM);
  - F2, F3… = UI подконтрольных устройств;
  - CMD+T — новый таб, CMD+1/CMD+0 — переключение табов, CMD+H — сплит по горизонтали, CMD+V — по вертикали;
  - программы запускаются клавишами 1/2/3 и через UI;
  - в будущем — группировка UI как в window managers.
- Кибер-миникарта: карта обнаруженных устройств и связей (туман войны до portscan).
- Реализация: DOM-оверлей поверх Babylon-канваса (терминальная CRT-эстетика, зелёный на чёрном).

### 5.5. Смерть хакера

- Захваченные устройства и трояны **остаются** (они в сети, не в голове).
- MEM деки теряется (украденные данные умирают вместе с хакером); MEM чужих
  хостов и захваченные устройства остаются (они в сети).
- Watcher-триггеры гаснут, но переподключаются быстро после респауна.

### 5.6. Дека

- Пресеты на старте + кастом: «Сканер» (NET+CPU), «Брутфорсер» (NPU), «Стелс» (RAM под trojan+watcher).
- Апгрейды деки по ходу геймплея (позже — уточнить источник апгрейдов: лут/фраги/данные).

## 6. Сеть как геометрия

- Устройства связаны **физическими кабелями** (видны в мире как жгуты вдоль стен/пола).
- Кабель **несекционируемый** (M2-2: механика перерубания удалена —
  портила играбельность). Топология сети меняется только захватом устройств.
  Прежнее правило (обрыв = недостижимость устройств за кабелем) удалено
  вместе с механикой: контр-хакинг бойцов — только огонь по хакеру в деке.
- **Switch** — узел коммутации: захватив, можно изолировать ветку сети.
- **Радио-точки** — беспроводной джек-ин в радиусе R (затухание сквозь стены —
  в полную версию; MVP просто радиус).
- Все устройства **нейтральные**: терминалы, точки, камеры — взламываются всеми.
  Владение = последний взломавший. Захваченный терминал можно залочить или
  читать лог подключений.

### 7.1. Физический сейф-эвакуация (CTF)

- Физический сейф (PHYSAFE) не в сети: подойти, space → взять (×0.5
  скорости, любой класс), отстреливаться можно, джек-ин нельзя.
- Два пути вскрытия: дотащить на базу (respawn-зона) ИЛИ ввести код на
  месте (код = `safe_key` из NETSAFE через cp+decrypt, §16).
- Доставка: +10 фрагов команде, затем канал «вскрываем 3 с» (прерывается
  уроном) → **извлечение = победа в матче** (гонка с фраговыми условиями,
  §16.0).
- Носитель роняет сейф при смерти (сейф остаётся лежать на месте смерти).
  Извлечение содержимого — **один раз за матч**.

## 8. Карты

- MVP-карта: 12–16 комнат, 2 этажа (лестницы с autostep), зеркальная
  симметрия, нейтральная сеть.
- Развёртка 2026-11-15 (под M4/M5, решение владельца: «данные на втором
  этаже, добавить лестницу»): на 2-м этаже уже терраса y=8 с центральной
  комнатой x21..43/z21..43 (будущий data-отсек M5) и 4 нишами; лестниц
  было две (СЗ/ЮВ) — добавлены **СВ и ЮЗ** (4 всего, зеркальная симметрия),
  с проёмами в плите террасы x48.2..53.5/z2..4 и x10.5..15.8/z60..62
  (ширина проёма = ширина лестницы 2 м, как у существующих шахт).
- Терминалы: 2 проводных + 1–2 радио-точки на contested-позициях (не на спавнах).
- Стиль: воксель-киберпанк (циан/маджента на тёмном), hacker view — CRT-терминал.
- Будущее: редактор карт (формат карты — данные, см. архитектуру).

## 9. Архитектура реализации

### 9.1. Общий контур

- **Сервер (Go)** — единственный источник истины: движение, урон, симуляция
  кибер-слоя (дискретно, в тик 30 Гц), владение устройствами, vision-зоны,
  счёт. Комната = одна горутина (паттерн уже в `server/main.go`).
- **Клиент (TS + Babylon.js)** — рендер, инпут, интерполяция снапшотов
  (66 мс в прошлом, было ~100; ред. 2026-11-17 §15.13 — mobile-tap lag;
  lag-compensation сервера синхронизирована: `rewindTicks=2`), автоогонь
  (клиент определяет «курсор на цели» и шлёт intent), DOM-оверлеи (HUD,
  hacker view).
- Транспорт: JSON поверх WS (MVP) → бинарный формат позже.
- Карта — данные (JSON), раздаётся сервером: `GET /api/map` — единый источник
  геометрии для сервера и клиента. Прокси: vite `/api` в dev, nginx `/api` в docker.

### 9.2. Wire protocol v0 (M1)

Клиент → сервер:
```jsonc
{"t":"join","name":"...","cls":"sniper|assault|heavy|hacker","team":-1} // team: -1=авто; 0|1=просьба (уважается, если не создаёт перекос ≥2); name уникально в комнате (дубликат → суффикс -2, -3…)
{"t":"input","seq":1,"keys":{"w":1,"a":0,"s":0,"d":1,"interact":0},"yaw":1.2,"pitch":-0.1} // ~30/с
{"t":"fire","yaw":1.2,"pitch":-0.1}                              // intent автоогня
{"t":"respawn","cls":"assault"}                                  // после таймера смерти
```

Сервер → клиент:
```jsonc
{"t":"welcome","id":7,"team":1,"tick":1234}
{"t":"snap","tick":1300,"now":169...,"players":[{"id":7,"name":"...","team":1,"cls":"assault","x":1,"y":2,"z":3,"yaw":0,"pitch":0,"hp":125,"alive":true,"safe":false,"jacked":true}],"scores":[24,31],"timeLeft":342}
// jacked (omitempty, M2): хакер стоит в деке; клиент по флагу самоисцеляет
// десинк «сервер джекнут, дека не показана» — шлёт jackout сам (§11)
{"t":"shot","by":7,"hit":9,"from":[1,2,3],"to":[4,5,6]}          // трассер/киллфид; hit может быть null
{"t":"death","by":9,"respawnAt":169...}                          // жертве; ред. 2026-11-17:
//      досылается мёртвому также при возврате из F5-сессии (by=-1 — убийца
//      неизвестен, respawnAt=now, сразу после welcome) — иначе оверлей респавна
//      не появляется и мёртвый игрок застревает без кнопки (§11, §12 «Сессии
//      по имени»). by=0 по-прежнему = среда/ловушка (§14.3), не смешивать
{"t":"team","team":1}                                             // авто-ребаланс перекинул игрока (респаун на новой базе)
{"t":"matchend","winner":1,"scores":[50,31]}                     // winner: 0|1|-1 (ничья); далее сброс и новый матч
```

**Конвенции координат** (обязательны для обеих сторон):
- `x,y,z` — позиция **ног** игрока (глаза = y+1.6, тело AABB 0.6×1.8×0.6);
- `yaw` — вавилоновская LH-конвенция: 0 → смотрит в +Z, положительное значение — поворот по часовой стрелке (сверху), радианы;
- `pitch` — ±89°, положительный — вверх, радианы;
- `from/to` в shot — мировые координаты глаз стрелка и точки попадания (или дальнего конца луча при промахе).

Формат карты (`/api/map`):
```jsonc
{"name":"m1","bounds":[64,16,64],
 "colliders":[{"min":[0,0,0],"max":[64,1,64],"kind":"floor"}, ...],   // AABB, kind: floor|wall|stair
 "spawns":{"0":[[x,y,z],...],"1":[[x,y,z],...]},                      // по командам
 "props":[]}                                                          // M2+: устройства, кабели, сейфы
```

### 9.3. Движение (сервер, M1)

- Кинематический контроллер на AABB: скорость класса, гравитация 20 м/с²,
  autostep 0.55 м (лестницы = ступени-боксы), высота глаз 1.6 м, прыжка нет.
- Anti-cheat: сервер клампит скорость/частоту input, позиция только серверная.

### 9.4. Стрельба (M1)

- Клиент: автоогонь когда ray от камеры пересекает капсулу врага (или конус
  малости) → шлёт `fire` с направлением (не чаще темпа оружия).
- Сервер: валидирует темп; попадание засчитано, если луч **пересекает AABB
  цели — текущий или отмотанный на 3 тика (~100 мс, lag compensation под
  интерполяцию клиента 66 мс + сетевой/тиковый запас; ред. 2026-11-17:
  было 4 тика под прежние ~100 мс интерполяции, синхронизировано с §15.13)**
  — либо центр цели в конусе ~2° (мягкий
  bullet magnetism); LOS до центра цели должен быть чист. Ближайшая цель
  вдоль луча. История позиций — кольцо на 8 тиков на игрока.
  NB: проверка только «центр в конусе» (v0) отклоняла попадания в голову/
  грудь/ноги ближе ~10 м и по стрейфящимся целям — главный урок плейтеста M1.

### 9.5. Кибер-слой на сервере (M2+)

- Граф сети: устройства (хосты с CPU/NPU/RAM/NET) + каналы (кабель/радио).
- Планировщик: на каждый тик каждый процесс получает долю производительности
  пропорционально справедливому делению (round-robin слайсы); прогресс задач
  дискретный (у portscan «осталось 3.2 с при текущей загрузке»).
- Перерубленный кабель = удалённое ребро графа (восстановление — инженер? потом).

### 10.1. Бэклог идей (не этапы, без срока)

- **Режимы игры вокруг околохакерских сценариев с силовой поддержкой**
  (идея владельца, 2026-11-16): сценарные режимы — «вытащи данные» (M5-механика
  как цель режима), «саботаж / защита объекта», эвакуация/конвой и т.п., где
  хакер необходим, но реализует возможности силовая часть. Главный баланс-принцип:
  **играть только за хакера должно быть неинтересно** — хак создаёт возможности
  (двери, глаза, отключённая защита), а пользуется ими штурм; у хакера должны
  быть моменты физического риска/участия (джек-ин в поле, физический сейф,
  уязвимость его собственной деки — см. пункт ниже). Прорабатывать после M5/M6.
- **shutdown / wakeup / wipe электронных компонентов** (идея владельца,
  2026-11-16): хакерские программы вырубания/перезапуска устройств (камера,
  турель, дверь, switch) — shutdown (off), wakeup (reboot в строй), wipe
  (постоянный лом/сброс состояния). И оборотная сторона: **дека хакера как
  цель** — вражеский хакер может shutdown/wipe деку, силовые классы вырубают
  джек-ин физически (смерть = принудительный джек-аут, уже есть). Даёт
  хакер-vs-хакер игру и причину охранять позицию хакера. Баланс: wipe —
  дорогой/медленный, в пределах раунда; полная потеря деки фрустрирует.
  Прорабатывать после бэклог-режимов.
- **Вопрос на подумать: должен ли firewall пропускать союзников?** (идея
  владельца, 2026-11-16): сейчас firewall режет транзит для ВСЕХ чужих, включая
  союзников (в `firewallBlocksThrough` есть только исключение для хозяина,
  cyber.go). Варианты: (a) как есть — союзника отрезает, команда должна
  договариваться, чьи фильтры на каких узлах (мина своему = реальный риск,
  больше коммуникации); (b) пропускать союзников — firewall становится чисто
  вражеским инструментом, команде проще ставить «сплошную» оборону, но пропадает
  цена ошибки и координация. Балансовые следствия обоих вариантов посчитать при
  проработке (форы врагу, удобство соло-игры vs ценность командной игры).
  Прорабатывать вместе с бэклог-режимами (в сценарных режимах командная
  координация важнее).

## 12. M2 «Кибер-базис» — реализационная спецификация

> Контракт для серверного и клиентского агентов. Протокол менять только
> через владельца. Все числа — M2-константы, правятся через ГДД.

### 12.1. Срез M2

- Пропсы на карте (все нейтральные, §6): **2 терминала** (проводной джек-ин),
  **2 радио-точки** (беспроводной), **2 switch**, **кабели** (рёбра сети),
  **2 двери** с контроллерами (первый CONTROLLERS-объект)
- Джек-ин: `space` у терминала (радиус 2 м) или радио-точки (радиус 20 м);
  джек-аут: **CTRL/CMD+ALT+DEL**, мгновенно
- **Универсальный физический джек-ин «дорогой вход»** (решение владельца
  2026-11-17, плейтест M5): джек-ин возможен у **любого** сетевого устройства
  в радиусе 2 м (сервисный порт есть у каждого), не только у точек входа.
  Цены: у терминала/радио — как прежде, **мгновенно**; у прочих устройств
  (switch/door/camera/valve…) — **установка канала 6 с**: хакер стоит и ждёт,
  прогресс показывается клиенту (`jackprog`, 2 Гц). Прерывания: смерть,
  отход из радиуса 2 м (урон НЕ прерывает — «порт держит связь», решено не
  переусложнять), джек-аут тройкой невозможен (не в деке). Прогресс НЕ
  персистит (ушёл — начинай заново). NET деки = **худший** из кабелей
  устройства (МБ/с, §16.3) — «дорогой» и в смысле канала; у точек входа —
  как прежде (100/20). Contested `enemy_team` (ниже) применяется только к
  **точкам входа**: физический порт чужого устройства законом не закрыт —
  влез и ты внутри. Watcher-событие `jackin` — то же (§13.1): любой вход.
  Конкуренция портов (камера над проёмом двери): побеждает та, **на которую
  смотрим** — конус ~25° вокруг 3D-направления взгляда (yaw/pitch); вне
  конуса — ближайшая по горизонтальной дистанции (плейтест 2026-11-17:
  «space в зоне и точки, и камеры работал только на точку», затем «стоял
  у D1, а джекнулся в CAM3 над проёмом»).
  **Тот же этаж** (плейтест 2026-11-17: «в комнате только D1/D2, а хинт —
  D3»): цель — только устройства своего этажа, центр порта не дальше ±2.6 м
  по вертикали от глаз; устройство на другом этаже с теми же x/z сквозь
  перекрытие не джекается и не подсказывается. Дистанция порта —
  горизонтальная (камеры висят над головой на кронштейнах своего этажа).
- Дека хакера: CPU 1.0, NPU 0.5, RAM 4 слота; NET = канал точки входа
  (терминал 100 Мбит, радио 20)
- Программы: **portscan / vulnscan / trojan (userland)**; честные очереди:
  N параллельных программ = каждая 1/N скорости; графики загрузки в UI деки
- Дверь: trojan на контроллере → владелец управляет open/close из UI двери
- Двери **выезжают вертикально** (решение владельца после плейтеста M2);
  анимация ~0.3 с, коллизия снимается сервером по open
- **Закрытая дверь блокирует огонь и зрение**: сервер отклоняет попадания/
  трассеры сквозь неё (segmentBlockedAll), клиентский автоогонь не
  цепляет врагов за закрытой дверью; открытая — прозрачна (плейтест M2-2)
- Подсказка джек-ина у точки входа: «SPACE — ДЖЕК-ИН // …» (в радиусе);
  вне радиуса — «<точка> — N м (РАДИУС M М)»; не-хакеру — «ТОЛЬКО ХАКЕР»
- Hacker view: DOM-оверлей; тело стоит у терминала беззащитно; движение и
  автоогонь отключены; смерть = обычная смерть + авто-джек-аут
- **Точки входа contested** (ред. 2026-11-17, решение владельца — было
  «решение владельца» per-player): терминал/радио, захваченный trojan'ом
  хакера **чужой команды**, не пускает (`denied: enemy_team`) — перехват
  только из другого места сети; терминал **союзника-хакера** открыт для
  джек-ина своей команды (владение per-player, доступ — по команде).
- **Сессии по имени**: F5/обрыв восстанавливают команду, позицию, класс,
  hp, знания сети и владение устройствами (TTL 5 мин). Ред. 2026-11-17:
  Ревизия 2026-11-17: **явно выбранный на экране входа другой класс
  уважается** (владелец: «выбираю хакер — после рестарта всё равно не
  хакер») — сессия возвращает всё, кроме класса, если игрок попросил
  другой. И ремап владения/vulnedBy/watcherBy на новый id выполняется
  только при реальной смене id: реконнект под тем же id при безусловном
  delete стирал бы метки (нашёл TestSessionRestore).
  возврат **мёртвого** (hp=0, respawnAt=now) — сервер после `welcome` досылает
  ему приватный `death` (`by=0`, §9.2), иначе клиентский оверлей респавна не
  появляется и игрок застревает в мёртвом теле без кнопки (баг-репорт владельца
  2026-11-17: «яндекс» с 0 HP, без движения и jack-in).
- **Джек-аут из деки — ТОЛЬКО тройка Ctrl/Cmd+Alt+Del** (ред. 2026-11-15,
  решение владельца: фишка — «системный» жест, специально неудобно; ESC в
  деке принадлежит ей — палитра/меню). NB: на Windows Ctrl+Alt+Del
  перехватывается ОС и до страницы не доходит (Fn+Backspace на mac = code
  'Delete'); прежде был ESC/Backspace — снято
- **Hotkeys hacker view — plain T/W/H/V** (браузер резервирует Cmd/Ctrl+T/W),
  цифры/F1..F9 — переключение табов

### 12.2. Модель устройства (сервер)

```
device: { id, kind: terminal|radio|switch|door,
          cpu, npu, ram, netMbps, owner: playerId|null,
          trojan: { level: userland, owner } | null }
terminal: cpu 0.5, npu 0, ram 2, net 100 (wire)
radio:    cpu 0.1, npu 0, ram 1, net 20 (радиус 8 м)
switch:   cpu 0.2, npu 0, ram 1, net 100 (4 порта)
door:     cpu 0.2, npu 0, ram 1, net 100 (короткий кабель до switch)
deck (у хакера): cpu 1.0, npu 0.5, ram 4
```
Программы бегут НА ДЕКЕ (portscan/vulnscan — сканирование через сеть,
trojan после установки живёт на устройстве). RAM: каждая запущенная
программа занимает 1 слот деки (максимум 4 параллельных).

### 12.3. Кабели и двери в карте

`h2dm1.json` → `props: []` заполняется:
```
{"kind":"terminal","id":"t1","pos":[x,y,z]}
{"kind":"radio","id":"r1","pos":[x,y,z],"radius":20}
{"kind":"switch","id":"s1","pos":[x,y,z]}
{"kind":"door","id":"d1","pos":[x,y,z],"size":[w,h,depth],"axis":"x|z","to":"s1"}
{"kind":"camera","id":"cam1","pos":[x,y,z]}                    // M3 §13.7: сенсор, ~2.6 м
{"kind":"cable","id":"c1","from":"t1","to":"s1","points":[[x,y,z],...]}
```
Кабель — только визуализация ребра графа (M2-2: перерубание удалено).
**Радио-точка** имеет беспроводной аплинк
к ближайшему switch (не режется физически, NET-бутылочное горло — сама
точка 20 Мбит; на карте рисуется пунктиром). Дверь — AABB-коллайдер,
`open` отключает коллизию. Размещение: терминалы в базовых комнатах команд (по одному),
радио-точки в центральных contested-комнатах, switch'ы между, двери —
проходы из центральных комнат в смежные (обе команды могут взломать).

### 12.4. Программы (формулы M2)

- `portscan` — 2.0 с при полной CPU-доле; **прогрессивное открытие** (решение
  владельца 2026-11-14): один запуск добавляет один хоп от известных
  устройств; карта — живой вид сети
  исчезают со скана
- `vulnscan` — 3.0 с, цель `dev`; по завершении устройство «vulned»
  для этого хакера (M2: навсегда; ред. 2026-11-17 — чужая метка стирается
  установкой antivirus на устройстве, §13.6)
- `trojan` — 2.0 с, цель `dev`, требует vulnscan; успех → `owner=хакер`,
  уровень userland; двери: владелец получает toggle
- Прогресс в тике: `progress += dt * (1/N_запущенных)`; окончание — эффект

### 12.5. Протокол M2 (добавление к §9.2)

C→S:
```jsonc
{"t":"jackout"}
{"t":"run","prog":"portscan"}                       // портскан без цели
{"t":"run","prog":"vulnscan","dev":"d1"}
{"t":"run","prog":"trojan","dev":"d1"}
{"t":"ctrl","dev":"d1","action":"toggle"}           // только владелец trojan
```
S→C:
```jsonc
{"t":"jackin","host":"t1","deck":{"cpu":1.0,"npu":0.5,"ram":4,"net":100}}
{"t":"jackprog","dev":"s2","s":4.3}   // 2 Гц, только джек-инящемуся: осталось секунд установки канала (§12.1 «дорогой вход»); после прерывания молчание — клиент гасит подсказку
{"t":"deck","cpuLoad":0.5,"npuLoad":0,"ramUsed":2,"netLoad":0.1,
 "progs":[{"id":7,"prog":"vulnscan","dev":"d1","etaMs":1500}]}   // 2 Гц, только джекнутому
{"t":"scan","devices":[{"id":"d1","kind":"door","x":10,"y":1,"z":20,"owner":3,"links":["s1"],"vulned":true}]}  // после portscan/изменений и ПОВТОРНО при jackin при накопленных знаниях (плейтест M3: восстановление табов устройств; знания обрезаются по достижимости от новой точки входа); vulned:true — уязвимость найдена МОИМ vulnscan'ом (omitempty, доп. 2026-11-14: обратная связь «2 → результат»)
// scan.devices[].soft (доб. 2026-11-17): [{"p":"watcher","o":7},...] — резидентный софт устройства
// с хозяевами; omitempty. Виден ТОЛЬКО владельцу устройства (трояновому хозяину) — чужой состав
// софта не раскрываем (иначе watcher/firewall теряют ценность); остальные видят только owner.
// Панель «ПРОЦЕССЫ» в табе устройства hackview: секция «СОФТ» из soft + «СЕТЬ» (радар §13.1 №3)
// + журнал; у чужих устройств секции СОФТ нет.
{"t":"denied","reason":"ram_full|not_vulned|not_owner|not_jacked|no_los|too_far|antivirus|firewall_scan|enemy_team|cp_cancel|dup|mem_full",
 "dev":"s2",   // dev (omitempty) — где упёрся: firewall_scan (§13.5); antivirus тоже с dev;
               // enemy_team (§12.5, ред. 2026-11-17) — джек-ин в точку входа чужой команды, dev = id точки;
               // cp_cancel — id источника прерванного трансфера (§16.2)
 "prog":"cp",  // prog/data (omitempty, ред. 2026-11-18 «красный мигающий бар»):
 "data":"door_key"} // отказ data-операции cp/mv/rm несёт операцию и ключ —
                    // клиент рисует красную мигающую карточку, а не безличный тост
```
`snap` расширяется полем `props` (всем):
```jsonc
"props":[{"id":"d1","kind":"door","x":10,"y":1,"z":20,"open":false},
         {"id":"t1","kind":"terminal","x":..,"y":..,"z":..},
         {"id":"r1","kind":"radio","x":..,"y":..,"z":..,"radius":20}]
```
Джек-ин — через `input.keys.interact` (edge) рядом с терминалом/радио;
клиент ничего отдельного не шлёт.

### 12.6. Hacker view (клиент)

- Оверлей поверх канваса (DOM, CRT-стиль), активен пока `jackin` не закрыт
  `jackout`/смертью. Тело рендерится другим игрокам как стоящее.
- Тайловый WM: **F1** = дека, **F2…** = подконтрольные устройства (таб на
  устройство при появлении владения), **T** — палитра табов (тот же
  командный ввод, что у `/`, режим «таб»: `[фильтр устройства]` + Enter =
  открыть таб; напр. `T` → `cam2` → Enter), **W** — снять панель в сплите,
  а в одиночной панели закрыть таб (дека не закрывается), **H/V** — сплит
  активной панели по горизонтали/вертикали (до 4 панелей), переключение
  табов — **F1..F9**. Хоткеи WM — **без модификатора** (согласно решению
  §12.1): Cmd/Ctrl+T, Cmd/Ctrl+W и Cmd/Ctrl+1..9 резервирует браузер, они
  до страницы не доходят.
- Таб деки: графики загрузки CPU/NPU/RAM/NET (canvas-спарклайны, история
  30 с), список запущенных программ с ETA, кнопки/хоткеи **1–6** (plain) =
  portscan/vulnscan/trojan/watcher/firewall/antivirus (цель — выбранное
  устройство), карта сети
  (SVG: узлы = discovered устройства, цвет = владелец/нейтральный, линии =
  связи; туман до portscan), статус «NET: терминал 100 Мбит».
  Хоткеи **1–6 работают в любом табе** (дека, S/V/D/G/T/R/CAM — плейтест
  M4). Цель — **устройство активного таба**: смотришь на D1 — софт идёт на
  D1 (плейтест: раньше уходил на S1, с которого таб открыли); на деке цель —
  выбранная на карте сети, как раньше. ПРОБЕЛ = TOGGLE на табе своей
  двери/клапана — независимо от фокуса на кнопках (фикс плейтеста).
- Таб двери: индикатор open/closed, кнопка TOGGLE (шлёт `ctrl`).
- В FPS-виде: терминалы/радио/двери/кабели рендерятся как пропсы (дверь —
  меш, открывается поворотом; кабель — тонкая янтарная линия-жгут);
  подсказка «SPACE — ДЖЕК-ИН» при близости к
  терминалу/радио (хакер); миникарта — иконки пропсов.

### 12.7. Приёмка M2

- Go-тесты: очереди (2 программы = 2× дольше), BFS-достижимость с учётом
  джек-ин/аут правила (дальность, LOS не нужен), trojan → toggle
  только владельцем, denied-причины
- e2e (scripts/e2e_smoke.mjs, новый блок M2): джек-ин → portscan находит
  дверь → vulnscan → trojan → toggle (open=true в snap.props) → jackout
- Клиент: tsc strict, npm run build; ручной плейтест владельца

## 13. M3 «Дуэль хакеров» — реализационная спецификация

> Контракт по аналогии с §12 (M2). Один объект за итерацию; камера —
> следующая, здесь не описана. Все числа — M3-константы, правятся через ГДД.

### 13.1. Объект 1: watcher (ред. плейтеста M3 2026-11-15: инфраструктура разведки)

`watcher` (§5.2) — **датчик кибер-событий** на устройстве: хакер ставит
сенсор и получает разведданные трёх видов — мгновенные alert'ы, накопительный
журнал событий и радар джекнутых, с ретрансляцией союзникам. Никаких
аватаров — только процессы и уведомления (§1).

> Редакция 2026-11-15 (плейтест M3, решение владельца): watcher расширен из
> «одноразового датчика jack-in» в инфраструктуру разведки (№1 журнал, №2
> триггеры, №3 радар, №4 ретрансляция). Контрплей/выкуривание watcher'а —
> отклонено; комбо watcher+камера — M6.

Механика:

- Установка: `{"t":"run","prog":"watcher","dev":"d1"}` — программа деки, как
  trojan/vulnscan: цель должна быть обнаружена своим portscan'ом и достижима
  BFS от точки входа (denied-причины те же: `not_jacked`/`ram_full`/`too_far`);
  **vulnscan требуется на чужих/нейтральных устройствах** (ред. 2026-11-16,
  решение владельца (c) «vulnscan = отмычка для установки софта»: на своих
  (трояновых) — не нужен; прежнее «НЕ требуется» от 2026-11-14 снято как
  нелогичное в легенде). Цель — любое устройство (в т.ч. camera/switch).
- Работа: **1.0 с** при полной CPU-доле (обоснование баланса: пассивный
  слушатель без подбора уязвимостей — дешевле vulnscan'а 3.0 с; дороже
  мгновенного — установка должна занимать слот RAM и время, иначе watcher
  ставят «на всякий случай» на всю карту). Занимает 1 слот RAM деки на время
  установки; после завершения триггер живёт на устройстве и слот освобождается
  (аналог trojan). Один хакер — один watcher на устройство; разные хакеры —
  свои watcher'ы на одно устройство (каждому — свои alert/журнал/радар).
- **Триггеры на кибер-события** (№2): watcher срабатывает не только на
  jack-in, а на события на устройстве:
  - `jackin` — любой другой хакер успешно джек-инился (точка входа —
    терминал/радио);
  - `install` — любой другой хакер завершил установку программы
    (trojan/firewall/antivirus/watcher — чужой watcher на моём устройстве
    тоже событие: это разведсобытие, а не только атака);
  - `owner` — смена владельца устройства (чужой trojan завершился; в alert
    приходит с `prog:"trojan"`).
  Свои действия не триггерят. Отбитый antivirus'ом trojan НЕ триггерит
  (установки не было; хозяин antivirus'а получает свой alert §13.6).
  Хозяин может быть не в hackview — сообщение доставляется как обычное
  серверное: тост деки или янтарная строка в киллфиде HUD.
- **Журнал событий** (№1): пока на устройстве стоит хотя бы один watcher,
  сервер пишет ring-buffer **ёмкости 20 последних записей**: jack-in'ы,
  установки программ (trojan/firewall/antivirus/watcher), смена владельца,
  упоры чужого скана в firewall на этом устройстве (ev `scanhit`). Запись:
  `{tick, ev, who, prog?}` — тик + что + кто (свои события тоже пишутся:
  журнал — история устройства, а не только угроз). Хозяин watcher'а читает
  журнал в табе устройства hackview (блок «ЛОГ СОБЫТИЙ», последние сверху);
  записи приходят внутри `scan.devices[].log` — только для устройств с МОИМ
  watcher'ом (не раздуваем трафик остальным; scan и так пересылается на
  каждое событие устройства, новое сообщение не вводится).
- **Радар «жучок»** (№3): живому хозяину watcher'а с частотой **1 Гц**
  (каждые 30 тиков, как лента камеры §13.7 — только живому владельцу,
  джекнут или нет) приходит срез `radar`: список **джекнутых** хакеров в
  сегменте, достижимом BFS **от устройства** с watcher'ом. Достижимость
  per-player (§13.5): чужой firewall (вражеский относительно хозяина) на
  транзитном устройстве режет видимость радара — **сетевая сегментация
  работает против разведки**: спрятанный за фильтром сегмент радар не видит.
  В срезе по каждому: id/имя/команда/класс/точка входа (`host`); сам хозяин
  в срез не входит. Пустой срез тоже шлётся (UI честно показывает «чисто»).
  UI (ред. 2026-11-17, решение владельца — переименование): блок
  «ПРОЦЕССЫ» в табе устройства hackview, секция «СЕТЬ» (счётчик «В СЕГИ: N»
  + список); обновление на месте.
- **Ретрансляция союзникам** (№4): alert watcher'а (все события: jackin/
  install/owner) дублируется живым **союзникам** хозяина (та же команда,
  кроме самого хозяина и актора события): та же строка `alert` с полем
  `relay:true`. Союзнику — понятная строка в киллфид HUD:
  «WATCHER: T2 ← ИМЯ · СОБЫТИЕ» (не хакерская «W ▸»); в hackview союзника —
  тост деки. Пинг устройства на миникарте НЕ делается (конвейер миникарты —
  построчный canvas без слоя пингов; введение пина — отдельный объект,
  при необходимости M6 к миникарте-vision). Мёртвым союзникам не шлём (§5.5).
- Смерть хозяина: alert'ы/радар **гаснут** (не шлются, пока хозяин мёртв,
  §5.5), но watcher **не снимается**: после респауна переподключается
  мгновенно, без переустановки (живёт в сети, не в голове — как trojan).
  Журнал продолжает писаться (живёт на устройстве). Сессия по имени (F5)
  перемапливает watcher'ы на новый id, как владение устройствами.
- Обратная связь: устройство с МОИМ watcher'ом помечается на кибер-карте
  (`watched:true` в `scan`, янтарный пунктирный ореол на SVG).

### 13.2. Протокол M3 (добавление к §9.2/§12.5)

C→S:
```jsonc
{"t":"run","prog":"watcher","dev":"t2"}   // как trojan, vulnscan не нужен
{"t":"run","prog":"firewall","dev":"t2"}  // §13.5: цель — любое сетевое устройство (ред. 2026-11-15)
{"t":"run","prog":"antivirus","dev":"t2"} // §13.6: цель — любое устройство
```
S→C:
```jsonc
{"t":"alert","dev":"t2","who":9,"src":"watcher","ev":"jackin"}
                                                     // §13.1: хозяину watcher'а на t2: хакер 9 туда
                                                     // джек-инулся; ev — контекст события (§13.1, ред.
                                                     // плейтеста M3 2026-11-15)
{"t":"alert","dev":"t2","who":9,"src":"watcher","ev":"install","prog":"trojan"}
                                                     // чужая установка программы на устройство с моим
                                                     // watcher'ом; prog — какая программа
{"t":"alert","dev":"t2","who":9,"src":"watcher","ev":"owner","prog":"trojan"}
                                                     // смена владельца устройства с моим watcher'ом
{"t":"alert","dev":"t2","who":9,"src":"watcher","ev":"jackin","relay":true}
                                                     // §13.1 №4: дубль живому СОЮЗНИКУ хозяина (не
                                                     // самому хозяину и не актору); relay:true — метка
{"t":"alert","dev":"t2","who":9,"src":"firewall"}   // только хозяину firewall'а на t2:
                                                     // хакер 9 портсканом упёрся в фильтр
                                                     // (один alert на запуск скана, §13.5)
{"t":"alert","dev":"t2","who":9,"src":"antivirus"}  // только хозяину antivirus'а на t2:
                                                     // хакер 9 пытался поставить trojan — отбито
{"t":"cam","dev":"cam1","seen":[
  {"id":9,"name":"hack_123","team":1,"cls":"assault","x":30.5,"y":1,"z":24.2}]}
                                                     // §13.7: лента камеры — 2 Гц, только живому
                                                     // владельца trojan на камере (джекнут или нет);
                                                     // seen = живые игроки в зоне видимости (может
                                                     // быть пустым — «кадр» с пустой лентой чистит UI)
{"t":"radar","dev":"t2","who":[
  {"id":9,"name":"hack_123","team":1,"cls":"hacker","host":"t2"}]}
                                                     // §13.1 №3: радар-срез — 1 Гц, только живому
                                                     // хозяину watcher'а на t2 (джекнут или нет);
                                                     // who = джекнутые хакеры в сегменте, достижимом
                                                     // ОТ t2 (BFS; чужой firewall режет видимость);
                                                     // пустой список шлётся (UI: «сегмент чист»)
```
`src` — источник алерта (`watcher`|`firewall`|`antivirus`). `alert`
расширяется полями (omitempty, обратно совместимо — старый клиент
игнорирует неизвестные поля):
- `ev` — контекст события watcher'а: `jackin` (джек-ин) | `install`
  (чужая установка программы) | `owner` (смена владельца). Присутствует
  только у `src:"watcher"`; firewall/antivirus его не несут (там событие
  одно, `src` достаточно). Старые alert без `ev` трактуются как `jackin`.
- `prog` — какая программа вызвала событие (`install`/`owner`: trojan/
  firewall/antivirus/watcher). Только вместе с `ev`.
- `relay` — `true`, если это дубль живому союзнику хозяина watcher'а
  (§13.1 №4); сам хозяин получает alert без `relay`.
`scan.devices[]` расширяется полями (omitempty):
- `watched` — на устройстве стоит МОЙ watcher (личное знание, как `vulned`);
- `log` — журнал событий watcher'а (§13.1 №1): массив последних записей,
  только для устройств с МОИМ watcher'ом (не раздуваем трафик остальным).
  Запись: `{"tick":123,"ev":"jackin","who":9,"prog":"trojan"}` (ev/who
  обязательны; prog — omitempty). Порядок — от старых к новым (последняя в
  хвосте); ёмкость 20 записей, переполнение вытесняет старейшую.
- `firewalled` — на устройстве стоит чей-то firewall (наблюдаемый сетевой
  фильтр — виден ВСЕМ, кто открыл устройство portscan'ом, аналогично `owner`);
- `firewalledBy` — id хозяина firewall'а (§13.5: чей фильтр — для бейджа
  «FIREWALL: свой/союзный/чужой» на кибер-карте; omitempty, приходит вместе
  с `firewalled`);
- `antivirused` — на устройстве стоит чей-то antivirus (резидентный процесс
  наблюдаем из сети — виден ВСЕМ, кто открыл устройство, как `firewalled`).
`denied` получает причины `antivirus` (§13.6: установка trojan отбита
антвирусом). Причина `firewall` (jack-in отбит фильтром) УДАЛЕНА в редакции
§13.5 от 2026-11-15: firewall больше не запирает вход, а сегментирует сеть.
Обратная связь сканеру (плейтест M4): если portscan упёрся в чужой фильтр,
сканер получает `denied reason:"firewall_scan"` c `dev` — id хоста, за
которым фильтр (тост «СКАН УПОРСЯ В FIREWALL (S2) — НУЖЕН TROJAN НА ХОСТЕ»).
Скан при этом НЕ отменяется — открытое остаётся открытым; это уведомление об
усечении, не отказ (запуску оно не мешает). Хозяину фильтра — `alert`
«F ▸ …» как раньше.
Причина `bad_target` (ред. 2026-11-15: firewall ставится на любое сетевое
устройство) теперь относится только к несуществующим/неоткрытым целям и
фактически перекрыта `too_far` — остаётся в протоколе как зарезервированная
(несовместимых kind-ограничений у программ больше нет).
`snap.props[]` расширяется записью камеры (всем, для рендера и LED-индикатора
владельца; `owner` — omitempty, 0 = нейтральная):
```jsonc
{"id":"cam1","kind":"camera","x":32,"y":2.6,"z":26,"owner":7}
```
Кибер-миникарта (§13.8) новых полей НЕ вводит: ей хватает `scan.devices[]`
выше (координаты/владение/связи/статусы) и `snap.props` — координаты точек
кабеля не нужны, связи рисуются от устройства к устройству (как в SVG-карте
сети деки).

### 13.3. Клиент

- Дека: кнопки/хоткеи **4 = WATCHER**, **5 = FIREWALL**, **6 = ANTIVIRUS**
  (продолжение ряда 1/2/3 = portscan/vulnscan/trojan; цель — выбранное на
  карте устройство).
- `alert`: hackview активен → строка-уведомление деки (тост WM);
  hackview не активен → янтарная строка в киллфиде HUD:
  «W ▸ T2 ← ИМЯ» (watcher, ev=jackin) / «W ▸ T2 ← ИМЯ ▸ УСТАНОВКА»
  (ev=install, PROG) / «W ▸ T2 ← ИМЯ ▸ ВЛАДЕЛЕЦ» (ev=owner) /
  «F ▸ T2 ← ИМЯ» (firewall: чужой portscan упёрся в мой фильтр) /
  «A ▸ T2 ← ИМЯ» (antivirus, отбита попытка trojan).
- `alert` с `relay:true` — союзнику хозяина watcher'а (§13.1 №4): НЕ
  хакерская «W ▸», а понятная строка — в киллфид «WATCHER: T2 ← ИМЯ ·
  СОБЫТИЕ» (СОБЫТИЕ = «ДЖЕК-ИН» / «УСТАНОВКА PROG» / «СМЕНА ВЛАДЕЛЬЦА»),
  в hackview — тот же текст тостом. Пинг устройства на миникарте не делается
  (дорого: миникарта — построчный canvas, слой пингов вводится отдельным
  объектом при необходимости в M6).
- Журнал событий (§13.1 №1) — в табе устройства hackview, блок «ЛОГ
  СОБЫТИЙ»: последние сверху (reverse), строка `T<tick> · СОБЫТИЕ · КТО`;
  СОБЫТИЕ по ev (ДЖЕК-ИН / УСТАНОВКА PROG / ВЛАДЕЛЕЦ / УПОР-СКАН), КТО —
  имя цветом команды (или «Я» для своего). Пусто — «СОБЫТИЙ НЕТ».
  Показывается только если устройство watched (моё); журнал приходит в
  `scan.devices[].log` — обновляется на scan-перерисовке таба (журнал
  меняется только вместе со scan; радар-лента — точечное обновление).
- Радар-срез (§13.1 №3) — в табе устройства hackview, блок «РАДАР
  СЕГМЕНТА»: шапка «В СЕТИ: N» + строка на каждого джекнутого (имя цветом
  команды, класс, точка входа HOST). Пустой срез — «СЕГМЕНТ ЧИСТ». Обновление
  на месте (1 Гц), только в табе устройства с моим watcher'ом.
- Кибер-карта: моё устройство с watcher — янтарный пунктирный ореол;
  устройство с firewall — пунктирный ореол + бейдж «FW»: цвет и подпись
  по `firewalledBy` — свой/союзный голубой `#5fd7ff`, чужой маджента
  `#ff4dd2` (§13.5); связи за чужим firewall не рисуются — устройства за
  ним выпадает из скана (живой вид сети); устройство с antivirus (чьим бы
  то ни было) — фиолетовый пунктирный ореол.
- Карта сети, пан/зум и declutter (плейтест M3, 2026-11-15): базовый viewBox
  480×360 (было 340×250); зум колесом/pinch 0.6×–5× к точке курсора, пан —
  drag ЛКМ или одним пальцем (порог 4 px: меньше — это клик = выбор цели),
  двойной клик — сброс; центр клампится так, что видимая область не выходит
  за базовый прямоугольник карты (при zoom < 1 центр фиксирован). Укладка
  узлов: лёгкий declutter — пары ближе 30 px раздвигаются (2 прохода, без
  физики). Подписи id — 8 px с тёмной полупрозрачной подложкой-плашкой;
  бейдж firewall короткий «FW» (цвет = свой/чужой), полный текст в tooltip.
- Камера (§13.7): 3D-меш с LED-индикатором владельца (нейтральная — тускло-
  серый, своя — зелёный, чужая — маджента; из `snap.props[].owner`); в
  hackview таб захваченной камеры показывает ленту `cam` — карточку-«рапорт»
  (шапка: id камеры / статус ЗАХВАЧЕНА / uptime ленты T+мм:сс / счётчик
  целей; каждая цель — строка-«профиль»: имя цветом команды, класс,
  дистанция до объектива в метрах, азимут, сектор движения), обновляется на
  месте без перестройки DOM. Пустой кадр — стейт «СЕКТОР ЧИСТ» + частота
  кадра + последний контакт («имя, N с назад»). Дистанция/азимут/движение
  клиент считает из кадра + позиции камеры из scan — протокол не меняется.
  «Картинка в UI» для MVP — этот рапорт; видео-рендер — M7+ полировка.
  Зона видимости на миникарте — объект M6, не сейчас.
- Слэш-палитра (плейтест M3, 2026-11-15): в активной панели деки `/`
  открывает командную строку внизу дека — запуск программ с клавиатуры,
  без мыши. Синтаксис `[фильтр устройства] [программа]`, оба токена
  опциональны на лету: `/cam1 port` фильтрует устройства по подстроке
  (id или kind: term/radio/switch/door/cam), затем программы
  (`portscan vulnscan trojan watcher firewall antivirus` + команда
  `data`, rus-алиасов нет). Tab — автодополнение первого кандидата (сначала устройства,
  потом программы), повторный Tab или ↑/↓ — цикл по кандидатам, Enter —
  запуск: portscan без цели, остальные — с до-поленной целью из токена
  (пустой токен устройства — текущая выбранная цель); Enter на кандидате-
  устройстве без программы — выбор цели, палитра остаётся открытой.
  Обратный порядок токенов тоже валиден (плейтест M4, desktop):
  `/portscan cam1` = «сначала программа, потом цель». Первый токен, который
  совпадает с программой и НЕ совпадает ни с одним устройством, считается
  программой — Tab тогда дополняет устройства во втором токене (список
  целей с подсказкой владельца). Enter с одной лишь программой (`/portscan
  ⏎`) — запуск на текущей выбранной цели (та же семантика пустого токена
  устройства; portscan — по всей сети). На touch это не действует: палитра-
  дерево всегда «сначала цель, потом программа» (§15.7).
  Esc — закрыть без запуска. Под строкой — список кандидатов
  (устройства с kind и статусом владения, программы), live-фильтрация по
  мере ввода. ↑ при пустой строке — предыдущая команда из истории сессии
  (localStorage не нужен). Кандидаты — только устройства из текущего
  скана (unknown не предлагать). Пока палитра открыта, дека-хоткеи
  (F-табы, plain T/W/H/V, Digit, Ctrl/Cmd+…) заблокированы, кроме
  CTRL/CMD+ALT+DEL.
  Раскладка не EN-US (плейтест M5, desktop): клавиши `Key[A-Z]` вводятся в
  строку палитры **латиницей по физкоду** независимо от раскладки (русская
  раскладка давала «саш1» вместо «cam1» — фильтры/запуск не матчились,
  тестирование превращалось в жонглирование раскладками); латинские раскладки
  и мёртвые клавиши (Ctrl/Cmd/Alt-комбинации, IME-композиция) не трогаются.
  Тот же принцип, что у `/` по `e.code`.
  **Команда данных** (M5 §16.2, 2026-11-18): `data [host] ls|cp|mv|rm …` —
  свой контекст-парсер по токенам: после `data` — хосты (вкл. `deck`) и
  подкоманды, после `cp`/`rm` — ключи данных (только свои хосты/дека,
  формат `key` либо `key@host` при неоднозначности), после ключа у `cp` —
  приёмники. Обратный порядок тоже валиден (`t1 data cp …`). Листинг `ls`
  рендерится прямо в списке кандидатов палитры (см. §16.2). Если открыт
  таб устройства с данными (или дека с items) — сами items становятся
  кандидатами первого токена: `door_key cp t2` / `door_key rm`. Кнопка
  `7 DATA` в ряду деки открывает палитру сразу с листингом активного
  таба; Digit8 свободен.
  Запуск шлёт тот же `{"t":"run"}` и уважает те же гейты — denied-тосты
  приходят как обычно.

### 13.3.1. Карта сети деки — ярусы-полосы по этажам (решение владельца, M4; ред. плейтеста)

Flat-XZ projection после появления 2-го этажа складывала узлы в кучу (s3
наезжал на s1/s2). Первая правка подняла ярусы ISO-накидкой (lift+shift) —
владелец отверг: **полосы этажей не должны пересекать друг друга**, а дека в
угле выглядела «вне этажей». Финальная схема (инвариант 7 — DOM/SVG, не 3D):

- высота `y<4 → Э1`, `y<11 → Э2` (пороги от реальных плит m1);
- каждый ярус — **горизонтальная полоса** на всю ширину с собственной
  подложкой-«этажеркой», подписью «ЭN» и СВОИМ fit по своему bbox: полосы
  не пересекаются по построению;
- declutter (раздвижение узлов до сходимости) с клампом ВНУТРИ СВОЕЙ полосы
  — узел никогда не покидает этаж;
- связь между ярусами (стояк c9 s2→s3) — голубой пунктир `.svg-riser`,
  единственный разрешённый «мост» через зазор, читается как «сквозь
  перекрытие»;
- **дека — не в углу**: узел ставится на ~40 px от хост-устройства (терминал
  или радио-точка джек-ина) в сторону центра его полосы, с подписью
  «ДЕКА·T2»; клампится в полосу хоста.
- одноэтажная сеть = одна полоса на всю высоту ≈ прежняя проекция; протокол
  не менялся (`scan.devices[].y` уже в wire, кластеризация клиентская).

### 13.5. Объект 2: firewall (сетевая сегментация)

`firewall` (§5.2 «фильтрует доступ по NET-интерфейсам») — оборонительная
программа дуэли хакеров: сетевой фильтр, режущий **трафик через устройство** —
как реальный firewall сегментирует сеть. Никаких аватаров — только процессы
(§1): firewall против чужого portscan, как antivirus против чужого trojan.

> Редакция 2026-11-15 (плейтест M3): прежняя семантика «магический замок на
> jack-in» (чужой вход в D = denied firewall) заменена сетевой сегментацией.
> Замок входа удалён; denied-причина `firewall` ушла из протокола (§13.2).

Механика (M3-срез — фильтр транзитного трафика):

- Установка: `{"t":"run","prog":"firewall","dev":"t2"}` — программа деки.
  Цель — **любое сетевое устройство**: terminal, radio, switch, door,
  camera (редакция плейтеста M3 2026-11-15: switch — классическое место
  firewall'а — режет межкоммутаторный линк s1↔s2 и разрезает карту пополам;
  конечные устройства (дверь/камера) тоже можно защищать от чужого
  portscan/доступа через них; прежде целью были только terminal|radio).
  Цель должна быть обнаружена своим portscan'ом и
  достижима BFS от точки входа (`too_far`); **vulnscan требуется на чужих/
  нейтральных устройствах** (ред. 2026-11-16, решение владельца (c) — как
  у watcher'а; на своих (трояновых) — не нужен; прежнее «НЕ требуется»
  снято). Firewall принадлежит установившему (id) и его команде.
- Работа: **1.5 с** при полной CPU-доле (обоснование баланса: активный
  фильтр дороже пассивного слушателя watcher 1.0 с, но дешевле эксплойта
  trojan 2.0 с). Занимает 1 слот RAM деки на время установки; после
  завершения фильтр живёт на устройстве, слот освобождается (как trojan).
  Один хакер — один firewall на устройство (повторная установка — no-op/перезапись).
- Эффект — сегментация: для **чужих** хакеров (вражеская команда)
  portscan/BFS не распространяется **через** устройство D:
  - сам D остаётся в скане (интерфейс виден), но соседи за D не открываются;
  - ранее открытое «за D» гаснет из скана — карта остаётся живым видом сети
    (§12.7-семантика): знания режутся при установке фильтра, при jackin и
    при каждом portscan;
  - джек-ин в САМО устройство D чужим **не блокируется** (замок входа
    убран) — но скан из D упирается в фильтр: распространение «от D» — это
    тоже трафик через D, чужаку из D виден только сам D;
  - достижимость считается **per-player** (run-валидация использует ту же
    матрицу: цель за чужим firewall = недостижима = `too_far`).
  Владелец фильтра и его союзники проходят свободно (командная игра: свой
  firewall не должен запирать свою же команду).
- **Firewall не молчит**: чужой portscan, упёршийся в фильтр (frontier-хост
  с чужим firewall имеет неоткрытых соседей — «попытка раскрыть сегмент за
  D»), шлёт хозяину фильтра `{"t":"alert","src":"firewall"}` — **один alert
  на запуск скана**, без спама (живому; мёртвым не шлём, §5.5). Атакующий
  со своей стороны видит бейдж FIREWALL на D (см. ниже) — он понимает, что
  сегмент закрыт, и ищет обход.
- Обходы (тупика нет):
  - **другая точка входа в тот же сегмент** — второй терминал или
    радио-аплинк внутри отрезанного сегмента (радио всегда ведёт к
    ближайшему switch, §12.3): скан оттуда раскрывает сегмент, не проходя
    через D;
  - **vulnscan + trojan на D** — trojan при смене владельца выкуривает
    чужой firewall (как в первой редакции), сегмент снова открыт (и уже
    сам закрыт contested-правилом для прежнего хозяина);
  - meatspace: убить хакера в деке (тело беззащитно, §12.6). Смерть
    гасит процессы его деки (авто-джек-аут отменяет запуски), но firewall
    живёт в сети (как trojan) — исчезают только alert'ы, пока хозяин мёртв.
- Смерть/сессия: как trojan/watcher/antivirus — фильтр остаётся в сети,
  alert'ы гаснут на время смерти; F5 перемапливает владельца на новый id.

**Точки входа под чужим firewall** (зафиксировано плейтестом M3 2026-11-15 —
семантика «вход есть, потока нет»; распространяется на все точки входа,
включая радио r1/r2):

- jack-in в устройство с чужим firewall'ом **проходит** — замка входа нет
  (см. выше: «джек-ин в САМО устройство D чужим не блокируется»);
- но весь трафик сквозь него для чужака мёртв: portscan из этой точки не
  раскрывает сеть — распространение «от D» это тоже трафик через D,
  чужаку из D виден только сам D;
- чтобы восстановить поток, надо **vulnscan + trojan на это устройство** —
  trojan при смене владельца выкуривает чужой firewall (уже реализовано);
- без firewall точка входа ломается «легко»: просто jack-in и portscan.

  Для радио-точек r1/r2 — то же самое: без firewall беспроводной вход
  берётся легко (jack-in в радиусе + скан), с firewall на радио — сначала
  выкуривание (vulnscan + trojan), потом скан.
- Обратная связь на карте: устройство с firewall помечается в `scan`
  `firewalled:true` + `firewalledBy:<playerId>` — **всем**, кто открыл его
  portscan'ом (сетевой фильтр наблюдаем из сети, в отличие от личных
  vulned/watched). Клиент рисует пунктирный ореол + бейдж «FW» с цветом по
  владельцу (свой/союзный — голубой `#5fd7ff`, чужой — маджента `#ff4dd2`).
  Рёбра за чужим firewall на карте **не рисуются** — устройства за ним
  выпадают из скана, сегмент визуально отсечён.

### 13.6. Объект 3: antivirus

`antivirus` (§5.2 «мешает установке trojan, может быть пробит — гонка
версий») — оборонительная программа дуэли хакеров: резидентный антивирус на
устройстве. PvP хакеров — дуэль процессами (§1): firewall против чужого
portscan (сегментация), antivirus — против чужого trojan.

Механика (M3-срез — блокироватор установки trojan):

- Установка: `{"t":"run","prog":"antivirus","dev":"d1"}` — программа деки.
  Цель — **любое устройство** (trojan ставится на всё, включая двери и
  switch'и — защищать есть что; denied-причины те же: `not_jacked`/
  `ram_full`/`too_far`). Цель должна быть обнаружена своим portscan'ом и
  достижима BFS от точки входа; **vulnscan требуется на чужих/нейтральных
  устройствах** (ред. 2026-11-16, решение владельца (c) — как у
  watcher'а/firewall'а; на своих (трояновых) — не нужен).
- Работа: **1.5 с** при полной CPU-доле (обоснование баланса: тот же ярус,
  что firewall — активная защита; дороже пассивного watcher 1.0 с, дешевле
  эксплойта trojan 2.0 с). Занимает 1 слот RAM деки на время установки;
  после завершения процесс живёт на устройстве, слот освобождается (как
  trojan/firewall). Один antivirus на устройство (повторная установка тем же
  хакером — no-op, чужая — перезаписывает хозяина: устройство не резиновое).
- Эффект: чужой (вражеская команда) trojan, завершившийся на устройстве,
  **отбивается** — `denied: antivirus` атакующему, владение НЕ переходит,
  чужой firewall на устройстве НЕ выкуривается (выкуривание — часть эффекта
  trojan, а trojan провалился). Отбитая попытка шлёт хозяину antivirus'а
  `{"t":"alert","src":"antivirus"}` (живому; мёртвым не шлём, §5.5 — как
  watcher/firewall). Отбитый trojan watcher'а НЕ триггерит (триггер
  watcher'а стоит на jack-in, входа не было — по аналогии с §13.5).
  Свой и союзный trojan проходит свободно.
- **Гонка версий** (решение 2026-11-14): antivirus **изнашивается** — отбив
  один чужой trojan, он снимается (сигнатуры устарели, фильтр пробит со
  второй попытки). Повторная попытка trojan тем же атакующим проходит:
  vulnscan не устаревает (M2: навсегда), перезапуск trojan — 2.0 с.
  Защитник может переустановить antivirus (1.5 с) и снова отбить — у кого
  быстрее и внимательнее, тот и выиграл дуэль версий. Семантика простая и
  детерминированная: «одна установка = одна отбитая попытка»; никакого RNG.
- Тупика нет (пути атакующего): перезапуск trojan против изношенного
  antivirus, trojan по другому устройству, meatspace-убийство хакера в деке
  (тело беззащитно, §12.6). Знание vulnscan не сгорает — повторный запуск
  доступен сразу (но см. ниже: чужая метка стирается установкой antivirus).
- **Антивирус стирает чужие vuln-метки** (решение владельца 2026-11-17,
  «пере-вскрытие после AV»): завершившаяся установка antivirus удаляет из
  `vulnedBy` устройства **все чужие** метки (метка самого установщика
  остаётся — он вскрыл устройство, чтобы поставить AV). Следствие: после
  AV чужие watcher/firewall/antivirus/trojan снова требуют vulnscan
  (`denied not_vulned`, §13.1) — защитник откатывает устройство в «закрытое»
  состояние за 1.5 с. Журнал устройства фиксирует `wipe` (все видят
  «кто-то чистил уязвимости», но не кого именно). Правка правила M2
  «vulnscan навсегда»: навсегда, пока не встал antivirus.
- Смерть/сессия: как trojan/watcher/firewall — процесс остаётся на
  устройстве (живёт в сети), alert'ы гаснут на время смерти; F5 перемапливает
  `antivirused` на новый id.
- Обратная связь: устройство с antivirus помечается на кибер-карте
  `antivirused:true` в `scan` — **всем**, кто открыл его portscan'ом
  (резидентный процесс наблюдаем из сети, как firewall); фиолетовый
  пунктирный ореол на SVG. Снятие (износ/перезапись) убирает отметку —
  атакующий видит из карты сети, что устройство снова открыто.

### 13.7. Объект 4: камера

Камера (§7 каталог №1, категория «Сенсор») — устройство наблюдения в сети.
Ключевое отличие от двери: **сенсор не воздействует на физический мир** —
нет контроллеров, есть только лента наблюдения для владельца. PvP-дуэль
распространяется и на неё: камера — обычное сетевое устройство, на неё
действуют все правила M3 (см. «Интеракции» ниже).

Устройство:

- Железо (как switch, §12.2): cpu 0.2, npu 0, ram 1, net 100. Размещается на
  карте (`h2dm1.json`, kind `camera`) на высоте ~2.6 м; кабелем включается в
  сеть (рёбра — только cable-пропсы, §12.3). Не точка входа: джек-ин у
  камеры невозможен.
- **Зона видимости (баланс, фикс)**: живые игроки в **радиусе 12 м** от точки
  установки (3D-дистанция) при **чистой прямой видимости** от объектива до
  центра корпуса игрока (ноги + 0.9 м): статика карты + закрытые двери
  (segmentBlockedAll, как у пуль — камера за стеной/дверью не «рентгенит»).
  Конус обзора + вращение камеры (направленный сектор, поворот из деки
  владельцем, автопатрулирование) — **объект M6** (запись в §10; решено
  2026-11-15, плейтест M3); сейчас радиус+LOS достаточно для геймплея
  «камера сторожит комнату»; затухание/помехи — нет.
- Захват: **trojan**, как у двери — vulnscan (3.0 с) → trojan (2.0 с);
  владелец = последний взломавший (§6 «все устройства нейтральные»).

Лента («картинка в UI»):

- Захватив, владелец (живой; джекнутый или нет — как alert'ы, §5.5) получает
  сообщение `{"t":"cam",...}` с частотой **2 Гц** (каждые 15 тиков) по каждой
  своей камере: список видимых игроков с именем/классом/командой/позицией.
  Пустой список тоже присылается — «кадр» чистит ленту UI. Мёртвым владельцам
  лента не шлётся (но владение сохраняется — после респауна лента возобновляется
  сама, как watcher-триггеры).
- Клиентский рендер MVP — карточка-«рапорт» в табе hackview (F2+ = UI
  подконтрольных устройств, §5.4; правка плейтеста M3 — вместо голого
  списка): шапка (id камеры, статус ЗАХВАЧЕНА, uptime ленты T+мм:сс от
  первого кадра, счётчик целей) + строка-«профиль» на каждую цель — имя
  цветом команды (зелёный/маджента, как ростеры), класс, дистанция до
  объектива (3D до центра корпуса: ноги + 0.9 м — та же точка, куда считает
  радиус сервер), азимут от камеры (0–360°, север = −Z) и сектор движения
  (↑↗→… из Δ двух кадров; сместился < 0.3 м — «·» = стоит). Всё считается на
  клиенте из кадра + позиции камеры из `scan.devices[]` — протокол НЕ
  расширяется. Пустой кадр — стейт «СЕКТОР ЧИСТ · КАДР 2 Гц · последний
  контакт: имя, N с назад» (клиент помнит последний замеченный контакт;
  контактов не было — «КОНТАКТОВ НЕ БЫЛО»). Обновление точечное, без
  перестройки DOM (2 Гц). Видео-рендер с текстурами — **M7+ полировка**
  (YAGNI).
- 3D: меш камеры с LED-индикатором владения (нейтральная/своя/чужая) из
  `snap.props[].owner`.

Интеракции с M3 (камера — устройство в сети, правила общие):

- **firewall** на камере работает (цель — любое сетевое устройство,
  ред. плейтеста M3 2026-11-15, §13.5): режет чужой транзит/скан через неё;
- **antivirus** на камере работает: отбивает чужой trojan (denied antivirus +
  alert, износ) — защищать есть что;
- **watcher** на камере — ставится, но не срабатывает (триггер стоит на
  jack-in, §13.1, а камера не точка входа);
- смена владельца trojan'ом выкуривает чужой firewall (§13.5) и сбивается
  чужим antivirus (§13.6) — как на любом устройстве.

Зона видимости на миникарте — **объект этапа M6** (миникарта-vision: FOV
союзников + камеры, §10), в этой итерации НЕ реализуется.

### 13.8. Объект 5: кибер-миникарта

Кибер-миникарта (§5.4, §2 «чужие устройства видны после portscan») —
**кибер-слой на физической миникарте** (`client/src/minimap.ts`):
географический вид сети поверх стен — раскрытые устройства, их связи,
владение и статусы M3, зона видимости своих камер.

Решение о размещении (2026-11-14): слой на физической миникарте (FPS-вид),
а НЕ ещё один таб hackview — в деке уже есть топологическая карта сети
(SVG-граф на F1, §12.6), а `body.hackmode` CSS прячет `#minimap` в деке.
Кибер-миникарта нужна хакеру прежде всего вне деки — планировать движение
по карте, глядя где чьи устройства; ГДД §2 прямо относит «чужие устройства
после portscan» к строке «Миникарта».

Механика:

- **Протокол: БЕЗ изменений** — хватает `scan.devices[]` (id/kind/x/z/owner/
  links/vulned/watched/firewalled/antivirused, §12.5+§13.2) и геометрии
  миникарты; радиус зоны видимости камеры — константа 12 м (§13.7).
- **Видимость**: рисуются ТОЛЬКО устройства, раскрытые МОИМ portscan'ом
  (туман войны, §5.4; сервер — источник истины, клиент ничего не
  догадывается). Базовые глифы физических пропсов (терминалы и т.п. —
  видны в мире глазами) остаются как в M1/M2 — кибер-слой их дополняет,
  а не заменяет.
- **Знания персистентны** между джек-инами (как `devices` в hackview,
  §12.1): вышел из деки — кибер-миникарта остаётся.

Рендер (все числа/цвета зафиксированы, консистентно с картой сети hackview):

- Устройства: глифы по типу — те же, что у миникарты (терминал = квадрат,
  радио = круг с точкой, switch = ромб, дверь = линия open/closed,
  камера = «глаз»-кольцо).
- Связи (между раскрытыми устройствами, дедуп по паре): кабель — сплошная
  `rgba(55,255,155,0.35)`; беспроводная (радио-конец) — пунктир
  `rgba(255,210,55,0.5)` (как `svg-wireless` в деке).
- Владение: кольцо вокруг глифа — моё `#37ff9b` толщиной 2.5, союзник
  `#37ff9b` толщиной 2, враг `#ff4dd2` толщиной 2 (как LED камеры §13.7
  и кольца на 3D-карте/нете).
- Статусы (ореолы, как в деке): `vulned` — сплошное кольцо `#ffd237`;
  `watched` — пунктир `#ff9f43` (3-3); `firewalled` — пунктир (2-4) + бейдж
  «FW»: свой/союзный `#5fd7ff`, чужой `#ff4dd2` (цвет по `firewalledBy`,
  §13.5); `antivirused` — пунктир `#c792ea` (5-3). Радиусы ореолов 6–11 px
  (разведены, чтобы читались стопкой). Связи за чужим firewall не
  рисуются — устройства за ним выпадают из скана.
- **Зона видимости своих камер**: полупрозрачный диск
  `rgba(55,255,155,0.08)` + обводка `rgba(55,255,155,0.35)`, радиус 12 м,

  командное vision — M6).

## 14. M4 «Ловушки» — реализационная спецификация

> Контракт для серверного и клиентского агентов. Протокол менять только
> через владельца. Все числа — v0-константы, правятся плейтестами через ГДД.

### 14.1. Срез M4

Порядок объектов — как в §10: сначала **газовая камера** (объект 9, §14.2),
после её плейтеста — **пол-лава** (объект 7, секционный DoT с телеграфом).
Ловушки — «гейты» формулы §1: меняют проходимость карты, а не только счёт.

Общие правила ловушек (уже зафиксированы в §7):

- **FF ON**: бьют всех живых в объёме, своих и чужих одинаково;
- **очки за ловушку**: убийство НЕ даёт очков, если у устройства нет
  владельца; взведённая ловушка с trojan-владельцем приносит **+1 команде
  владельца** (решение владельца 2026-11-15: ценность взлома; victim==owner —
  очков нет, «сам в свой газ» не фармится); killfeed: owner>0 → имя владельца,
  owner=0 → «ЛОВУШКА»;
- урон серверный (invariant 1): клиент лишь рисует последствия из `snap`.

### 14.2. Объект 1: газовая камера

Физика: проп-объём `gas` с AABB (`pos` центр, `size` [w,h,d] — как дверь);
внутри объёма, пока клапан открыт, DoT. Утечка через двери/стены НЕ
моделируется — газ строго в AABB пропа (YAGNI; стены и двери и так физ-блоки).

Сетевая модель: газовый клапан — **такое же управляемое устройство, как
дверь**: kind `gas`, `to` → switch (сетевой сосед, как у doors), discovery
через portscan/vulnscan без исключений, владение через trojan, взводится
`ctrl` toggle владельцем (§12.5) — кнопкой в табе устройства и **ПРОБЕЛОМ**
на табе газа (тот же UX, что дверь, §13.3). Поле состояния переиспользуется
`open` = «клапан открыт / газ идёт».

Состояния и числа v0:

| Параметр | Значение |
|---|---|
| `GAS_DPS` | 8 HP/с (heavy 200 → 25 с, снайпер 100 → 12.5 с — «успел выбежать») |
| `GAS_TELEGRAPH` | 1.5 с мигания перед первым уроном после взвода |
| шаг урона | накопление float-долга, `damage` при целых очках |
| смерть | приватно `{"t":"death","by":0,"respawnAt":...}` жертве + broadcast `{"t":"envkill","victim":id,"owner":id}`; owner>0 и owner≠victim → +1 команде владельца, иначе счёт чист |

Сервер (комната-горутина, вне `interactTick`, до `broadcastSnap`):

1. `gasTick(dt)` в `simulateTick` (world.go, сразу после `cyberTick`): для
   каждого газа с `active`: телеграф-таймер (если `armAt` задан и
   `now < armAt + GAS_TELEGRAPH` — урона нет), иначе `box.contains(player.pos)`
   → накопление долга → `envDamage(pl, 8·dt)`;
2. `envDamage(pl, dmg)` — копия `combat.go damage` без стрелка: только hp,
   смерть → `respawnAt = now+5` + `jackout` (хакер в газе сгорел в meatspace)
   + `death by:0`; без `scores`;
3. `handleCtrl` разгрузить с `door`-гейта на `{door, gas}` (owner, jack, LOS
   — как дверь); `ctrl gas` ставит `active=true, armAt=now` / `active=false`
   (снятие гасит мгновенно);
4. snap props: газ несёт `open` (клапан) — телеграф клиент считает сам по
   моменту наблюдения flip'а (визуал, точность долей секунды не нужна).

Карта (`h2dm1.json`, invariant 6): **две зеркальные газовые комнаты** —
восточная у s2 и западная у s1 (решение владельца после плейтеста: «ловушек
одна — нечестно, симметрично»; восточная выбрана из-за двери d2 рядом —
тактика «закрыть дверь с жертвой внутри»):
`{"kind":"gas","id":"g1","pos":[47.5,1.5,33],"size":[5,3,6],"to":"s2"}` +
кабель `c8` g1→s2, и зеркало
`{"kind":"gas","id":"g2","pos":[16.5,1.5,31],"size":[5,3,6],"to":"s1"}` +
кабель `c14` s1→g2 (проверено: объём x14..19/z28..34 не пересекает ни один
не-floor коллайдер и спавны; в западном крыле рядом дверь d1). Две поправки
по ходу реализации:

- pos/size сдвинуты относительно первой прикидки (`[45,1.5,36]`/`[8,3,8]`) —
  та коробка пересекала стеновой коллайдер x42.5..43.5 и накрывала спавн
  команды 1 `[50,1,38]`; фактический объём x45..50, z30..36 проверен по всем
  не-половым коллайдерам, дверному плиту d2 и всем спавнам;
- `to` у пропа — **только ссылка для валидации/рендера**, реальная сетевая
  досягаемость (как у дверей d1/d2) идёт явным `cable`-пропом: без c8 газ
  не появился бы в portscan.

Клиент:

- рендер (`props.ts`): полупрозрачный бокс-объём; цвета: клапан закрыт —
  тусклый `rgba(55,255,155,0.06)` + каркас; телеграф (первые 1.5 с после
  observed flip→open) — жёлтое мигание каркаса; идёт газ — плотный
  `rgba(120,255,80,0.25)` + каркас `#7dff50`;
- деки: `KIND_LABEL` «ГАЗ», `KIND_ALIAS` (`gas`/`газ`), кнопка TOGGLE на
  табе газа + ПРОБЕЛ (гейт «свой таб» как у двери), статус-строка
  «КЛАПАН: ОТКРЫТ/ЗАКРЫТ»;
- миникарта: глиф газа (ромб с точкой);
- killfeed: broadcast `envkill` всем (`main.ts handleEnvKill`): `owner>0` →
  обычная строка «ВЛАДЕЛЕЦ ▸ жертва» (счёт тоже ведёт сервер), `owner=0` →
  «ЛОВУШКА ▸ жертва» (hud.killfeedEnv); приватный `death by:0` → оверлей
  жертве «УБИТ ▸ ЛОВУШКА» (в оверлее владельца не показываем — он мог
  умереть раньше); переход снапа затронутого envkill игрока не даёт
  `???`-дубля;
- damage-вигнетка бесплатна (hp-дифф snap, §main.ts).

Тесты: `gas_test.go` — armed+внутри → hp падает; смерть без владельца →
`death by:0`, `scores` не тронуты, respawn +5 с; смерть при trojan-владельце
→ +1 команде владельца, victim==owner → чисто; вне объёма — без урона; disarm гасит;
ctrl без владельца → `denied not_owner`; телеграф-окно — урона нет;
`map_test.go` — валидация kind `gas` (size обязателен, `to` → существующий
switch).

### 14.3. Протокол M4 (добавление к §9.2/§12.5/§13.2)

C→S без изменений (тот же `ctrl` toggle). S→C: `death.by = 0` — среда
(ловушка); `snap.props[]` для kind `gas` добавляет `open` (как door).

`death` исторически приватен жертве (`sendTo`), а киллфид обещан ВСЕМ
(§14.1) → broadcast-событие убийства средой:

```jsonc
{"t":"envkill","victim":7,"owner":3}  // owner — trojan-владелец устройства
                                      // (0 = нейтрали/нет); имя/команда — из snap
```

Порядок в flush тика: `death` → `envkill` → `snap`. Клиент на `envkill`
выводит строку киллфида и ставит штамп; последующий alive→dead переход
снапа этого id молча подавляется (иначе `???`-дубль). Сервер при owner>0 и
owner≠victim делает `scores[team(owner)]++`. Оверлей жертве — из приватного
`death by:0` («ЛОВУШКА», без имени владельца: owner к моменту смерти
жертвы мог уже лежать).

## 15. Мобильная адаптация (управление и дека на тапе)

Клиент определяет touch-режим по JavaScript-признакам (`pointer: coarse` /
`maxTouchPoints`), не по User-Agent: UI решает наличие пальца, а не бренд. При
детекте вешается `body.touch`, CSS и mobile.ts слушают класс; десктоп (мышь)
не получает оверлея вообще — нулевая регрессия. Протокол §9.2, симуляция и
инварианты не затронуты: оверлей пишет в те же `KeysState`/yaw/pitch, сервер
типа устройства не видит.

### 15.1 Meatview: touch-оверлей

- **Слева под большой палец — крестина движения**: четыре сегмента
  (верх/низ/лево/право = w/s/a/d) + центральный хаб; мультитач через pointer
  capture (одновременные «бег + прицел» работают), сброс при pointerup/cancel.
  *(Ред. 2026-11-17: крестина заменена аналоговым 9-позиционным стиком —
  §15.11; четыре глифа-стрелки остались только как индикация.)*
- **Справа — круг прицела** (схема Gun Bros): удержание и перетаскивание
  пальцем = смещение взгляда, чувствительность 0.0032 рад/px (мышь 0.0022);
  инверсия Y из настроек соблюдается; взгляд по-прежнему замораживается в деке.
- Огонь — автоогонь по LOS без изменений (§3.2); гейт `pointer lock` на touch
  заменён на «палец на круге прицела». requestLock на touch не запрашивается.
- **ДЕЙСТВИЕ** (=Space, edge-джэк-ин) — круглая кнопка справа над FIRE;
  респаун-кнопка в death-оверлее тапается без изменений.
- Все элементы внутри `env(safe-area-inset-*)`; viewport: `viewport-fit=cover`,
  масштабирование запрещено (это игра, не документ); `touch-action:none` на
  зонах оверлея, двойного тапа-зума нет.

### 15.2 Дека на тапе

- Кнопка **[ / ]** в ряду программ деки = эквивалент клавиши `/` (палитра
  §13.3). Кандидаты палитры тапаются: тап по строке = выбор+запуск (tab-режим:
  открытие таба). Enter/«Поиск» на экранной клавиатуре = запуск.
- **Палитра на touch открывается над экранной клавиатурой**: низ якоря
  считается от visualViewport (`--kb = innerHeight − vv.height − vv.offsetTop`,
  обновляется на resize), т.е. поле ввода над полем и над клавиатурой, а не у
  низа дека как на десктопе (там остаётся bottom: 34px под полем).
- Клавиатурные хоткеи деки не отменяются; на touch им в пару тап-элементы:
  чипы табов/кнопки программ (были), [ / ], кнопка **ВЫХОД** в шапке деки
  (заменяет Ctrl+Alt+Del — на телефоне жест физически недоступен); hotkey-
  footer на touch прячется. Тап-таргеты ≥ 40px (только под `body.touch`).

- 2026-11-15 (ред. владельца к updatewatch): период проверки 4 с → **30 с**,
  фейл фетча = экспоненциальный backoff ×2 до 4 мин, успех сбрасывает.

### 15.3 Join/death-оверлеи на телефоне

- Панель join не влезает по высоте → ДЕПЛОЙ был недостижим: flex-центрирование
  без скролла обрезало сверху. Исправлено: `.overlay { overflow:auto;
  align-items:flex-start }` + `.panel { margin:auto }` — по centre пока влезает,
  при переполнении скроллится пальцем (`touch-action: pan-y` только на
  оверлеях; глобальный `touch-action:none` на `body.touch` убран — он глушил
  скролл; игровые зоны несут none точечно: canvas, tc-*, netmap).
- Классы при ширине <720px идут в одну вертикальную колонку (медиазапрос по
  ширине, а не по `body.touch`: телефон в ландшафте тоже попадает; десктопное
  окно на узкой ширине получает то же адекватное поведение).

### 15.4 Landscape по ДЕПЛОЮ + компактные контролы (ревебр owner)

- **ДЕПЛОЙ на touch**: requestFullscreen + `screen.orientation.lock('landscape')`
  (lock доступен только в fullscreen — отсюда порядок; отказ браузера молча
  фолбэкается в окно). На iOS Safari API нет — эффект только в standalone (PWA
  «Домаш»). Снятие — при resetSession (возврат в лобби): unlock + exitFullscreen.
  Legacy-теги в index.html (`apple-mobile-web-app-capable` + status-bar-style +
  title): до iOS 16.4 modern display-mode не читается, ярлык без legacy-тега
  открывается закладкой в Safari. После деплоя ярлык нужно пересоздать (метатеги
  кэшируются в старом).
  На десктопе/клавиатуре ничего не происходит (гейт IS_TOUCH).
- **Контролы в ландшафте**: крестовина и круг прицела — в самих нижних углах
  под большие пальцы (offset 8px от края, были 96/104px снизу), размер 112px
  (было 148 — «в пол-экрана»), фон плотный (0.78–0.88 alpha, было 0.3–0.6),
  рамка/глифы приглушены (0.24–0.5, было 0.35–0.55) — «менее прозрачные и
  менее сильные». Подпись ПРИЦЕЛ тоньше (9px). Ревебр след.: контуры слишком
  тихие — рамки 2px ярче (0.55–0.6 + слабое свечение), глифы сегментов
  читаемые, на крестовине стрелки ▲▼◀▶ (апфорт направлений). Pointer capture ведёт drag за
  пределы кнопки — компакция круга не меняет угловое покрытие взгляда,
  чувствительность остаётся 0.0032 рад/px.
- Побочно: `.panel { max-width: min(860px,100%) }` — в ландшафте телефона
  панель join не распирать вьюпорт (карточки не клиппятся).

### 15.5 Экран настроек + mobile-HUD (ревебр owner: сенса, оверлей, ростер)

- **Сенса тач-прицела** ×3: базовая 0.0096 рад/px (было 0.0032).
- **Экран настроек** (ревебр owner: однотипно на всех платформах — старый

  ряду с ДЕПЛОЕМ (`flex-wrap`: рядом, если ширина позволяет, иначе перенос
  под неё) открывает модалку поверх join: инверсия взгляда + слайдер
  чувствительности 0.3×…3.0×. Множитель общий (`controls.sensScale`): на
  десктопе масштабирует мышиную сенсу (0.0022 рад/px), на touch — тач-прицел;
  персист `hs.lookSens`, live-применение. Закрытие — кнопка, клик по
  затемнению, ESC. Ревебр owner «на максимуме не хватает»: слайдер 0.3×…4.0×
  (база тач 0.0096 → до 0.0384 рад/px) + исправлен wiring: `applySens` в
  конструкторе Hud вызывался ДО назначения `hud.onSensScale` в main.ts —
  загруженная из localStorage сенса молча оставалась 1×. Теперь `reapplySens()`
  — публичный метод, main вызывает его сразу после wiring, deploy — на всякий
  случай. Побочно (тот же ревебр): фон tc-контролов снова полупрозрачный
  (0.28–0.5, контуров достаточно), на touchdeath-оверлей предвыбирает текущий
  класс (иначе тап по РЕСПАУН молча делал из хакера автоматчика — «не могу
  ничего сделать и переключиться в hackview»: серверная проба join+interact
  подтвердила, что гейт и тач-путь исправны, потеря класса была на клиенте).
- **Mobile meatview-HUD**: нижние углы эксклюзивны за tc-контролами — HP-щит
  под топбаром по центру, миникарта компактная (110px; portrait 86px) в
  top-right, киллфид под ней, ростер в одну строку (8px, ellipsis), `#debug`
  скрыт, jackinHint/propLabel компактнее и уходят из центра экрана.
  Десктопная раскладка не меняется: всё под `body.touch`.

### 15.6 Дека на тапе: компактные CPU/NPU/RAM/NET (ревебр owner: «слишком здоровые, по высоте»)

- Ревебр owner после первого мобильного плейтеста деки: плашки CPU/NPU/RAM/NET
  съедают полэкрана по высоте. На touch each sparkline — одна компактная строка
  «метка · график · значение» вместо двухъярусной карточки (шапка + канвас):
  label/value в одну строку с графиком по центру, канвас 20px в высоту, отступы
  урезаны, ряд спарклайнов узкий (gap 6px). При ширине меньше 560px сетка
  автоматом 4→2 колонки, чтобы значения не резались.
- Только CSS под `body.touch` (display:contents у шапки — DOM/разметка и
  отрисовка канваса общие с десктопом, TS не трогает). Десктоп не меняется:
  «старое в desktop менять нельзя, там идеальный UX».
- Ревебр owner той же итерации (все пункты — только touch, desktop не тронут):
  - **палитра — первой кнопкой** ряда программ (`order: -1` у `.hv-btn-slash`),
    и сам ряд компактнее (padding 5×8, 10px, gap 3; список процессов тоже
    плотный, min-height снят) — на 844×396 шесть кнопок + палитра влезают без
    вертикального скролла;
  - **графики сдвинуты вправо** в ландшафте (`margin-left: 252px` = ширина
    колонки программ + gap) — ряд CPU/NPU/RAM/NET висит над картой сети, а не
    над программами; в портрете (сетка 2×2) сдвиг не нужен;
  - **полоска-заголовок панели («ДЕКА») убрана** — её дублирует ряд чипов-табов
    (F1 ДЕКА / F2 …): `body.touch .pane-head { display: none }`; кнопка ×
    закрытия панели переехала в плавающий угол самой панели, иначе табы
    пришлось бы закрывать только W. Уточнение owner: только на мобиле.

### 15.7 Карта, связи, палитра-дерево (ревебр owner: «слишком мелко», «связи кликом», «клавиатура 90% экрана»)

- **Карта узлов на тапе — крупнее** (ревебр «максимально понятные элементы,
  слишком мелко»): базовый зум карты `NETMAP_ZOOM0 = 1.5` (на десктопе 1;
  pinch по-прежнему разматывает до 0.6 = вся карта, зумит до 5, дабл-тап —
  сброс к тач-базе) + `NETMAP_S = 1.45` масштаб геометрии (радиусы узлов,
  ореолы vulned/watcher/firewall/antivirus, подписи, стояки) — тап-таргеты
  и читаемость. Десктоп: константы равны 1, геометрия байт-в-байт прежняя.
- **СВЯЗИ в табе устройства — кликабельные чипы** (тап и клик, на DESKTOP
  тоже — прямое указание owner): каждый отсканированный сосед — кнопка,
  открывает его таб (`ensureTab`); не-просканированные ссылки остаются
  тусклым текстом (открыть нечего). Протокол не затронут — чистый UI.
- **Палитра на тапе — дерево кнопок вместо строки ввода** (ревебр «клава
  занимает 90% экрана»): системную клавиатуру iOS/Android веб уменьшить не
  может (нет API) — поэтому на touch поля ввода нет вовсе, клавиатура не
  вызывается: уровень 1 — PORTSCAN по всей сети + список устройств (тап →
  уровень 2; при непустой деке — и строка «ДЕКА: ДАННЫЕ (n)» → уровень
  items деки), уровень 2 — ← НАЗАД + шесть программ с подсказкой готовности
  (ГОТОВО / СНАЧАЛА VULNSCAN; тот же смысл, что у второго токена строки) +
  строка «ДАННЫЕ (n)» для устройства со своими данными → уровень items:
  строки-кнопки с CP (→ уровень приёмника: ДЕКА + свои хосты) и 🗑 RM
  (§16.2, 2026-11-18). Кнопка `7 DATA` открывает дерево сразу на уровне
  ДАННЫЕ активного таба (или деки).
  Палитра без `--kb`-отступа: `:has(.hv-pal-input)` отличает десктоп-раскладку.
  Десктоп — строка ввода с автофокусом, hotkey-путь побайтно прежний;
  кнопка `/ ПАЛИТРА` переиспользует тот же `openPalette`, только режим
  отображения другой. Открытое дерево обновляется на новый `scan`.

  только шумела. Убрана на **обеих** платформах по прямому слову owner («и на
  десктопе... итак хватает подсказок»): пустой список — пустой, подсказок
  достаточно (ряд кнопок программ, футер деки, палитра-дерево/строка).

### 15.9 Mobile: HP-щит слева вверху, FPS вместо дебага (ревебр owner)

- Ревебр owner: контрол с health на мобиле — **слева вверху** (в landscape
  левый низ занят крестиной, центр сверху мешал топбару/миникарте), а **под
  ним — FPS** на месте отключённой дебаг-панели (`#debug` под `body.touch`
  скрыт). FPS-чип `#fpsChip` (12px, моно, `NN FPS`), обновляется раз в секунду
  из `engine.getFps()` в render loop (дешевле, чем каждый кадр; `Math.round`).
  Чип виден только на touch: десктопский `#debug` остаётся единственной
  телеметрией (tick/rtt/snaps/players не переезжают — на телефоне они и не
  нужны). Чип — под `#vitals`, который на touch переехал из центра в левый
  угол под топбар; `#fpsChip` скрывается вместе с HUD в hackmode (`body.hackmode`).

### 15.10 Мобильная Дека: список процессов не лезет на «/ ПАЛИТРА» (ревебр owner)

- Ревебр owner: запущенные программы (строки с ETA) в левом верхнем углу деки
  перекрывали кнопку «/ ПАЛИТРА», просили сдвиг +10px. Первопричина глубже:
  `min-height:0` (§15.6) сделал бокс `.hv-progs` сжимаемым flex-элементом —
  при 4–5 процессах строки отрисовывались ниже сжатого бокса и наползали на
  ряд кнопок. Фикс touch-only: `flex:0 1 auto; min-height:44px; max-height:92px;
  overflow-y:auto` — бокс не режется изнутри (строки не вылезают за него при
  любом числе процессов), при нехватке места сжимается до пола в две видимые
  строки и прокручивается внутри; + добавочные 10px `padding-bottom` до ряда
  кнопок — ровно просьба owner. Desktop не затронут (правила под `body.touch`).

### 15.11 Move-стик: 9 позиций вместо 4 направлений (ревебр owner)

- Ревебр owner: палец на move-контроле лежит постоянно, поэтому «4 кнопки»
  не работают как контрол — нужен **аналоговый стик направления** (по аналогии
  с mlook: палец на площади, смещение = направление). Реализовано как 9
  состояний: **8 секторов по 45° + нейтраль** в мёртвой зоне центра. Глифовых
  стрелок по-прежнему **четыре** (▲▼◀▶): диагональные секторы подсвечивают две
  стрелки сразу.
- Вектор пальца `(dx,dy)` от центра стика → `atan2` → ближайший сектор;
  сектор → флаги `KeysState` (`E=d, SE=s+d, S=s, SW=a+s, W=a, NW=a+w, N=w,
  NE=w+d`). Серверный `wishDir` уже нормализует комбинированный вектор до
  единичного (`physics.go`), диагональный ход = полный ход как на клавиатуре
  (w+d). **Протокол §9.2 не меняется** — сервер типа контрола не видит.
- Нейтраль (стоп) — радиус `< PAD_DEAD` (18% полурадиуса, примерно визуальный
  хаб 30%): палец проходом через центр не дёргает тело.
- **Гистерезис секторов** `PAD_HYST=7°`: направление меняется, только когда
  угол пальца уходит за границу текущего сектора на 7° (эффективная ширина
  «цепляния» 38° против 52° внутри сектора). Без него палец у границы 45°
  chatter'ит между прямой и диагональю от микродвижений кожи. У самого края стика
  (радиус > 1.5 полурадиуса — вне отрисованного круга) захват ближайшего
  сектора без гистерезиса: там палец уже «на направлении», а не на границе.
- Сброс при pointerup/cancel/reset (вход в деку, смерть): сектор → нейтраль,
  все флаги движения в 0 — прежнее поведение.
- Desktop не затронут: оверлея на мыши нет вообще (§15); WASD-путь прежний.
  CSS стика (круг 112px, хаб, стрелки) не менялся — менялась только семантика
  хит-теста в mobile.ts.

### 15.12 Тап-меню паузы и tc-контролы: короткое касание стика не замораживает (баг-фикс 2026-11-17)

- Плейтест 2026-11-17 (mobile): «игрок не двигается». Первопричина не стик
  (e2e-проба touch-эмуляцией: удержание даёт 30/30 input-фреймов с флагом,
  сервер мотает позицию), а **меню паузы** (§15.5, комбо тап-по-экрану):
  короткий тап (<350 мс, <12 px) по ANY точке экрана открывал меню →
  `controls.frozen` → тело стоит. Со старыми 4 кнопками это было редко
  (сегменты — кликабельные зоны), с аналоговым стиком §15.11 палец по задумке
  ложится и отрывается постоянно — каждое короткое касание стика/прицела/
  ДЕЙСТВИЕ открывало меню, а тапом его уже не закрыть (гейт `!menuOpen`) —
  игрок «замирал» до нажатия ВЕРНУТЬСЯ В БОЙ.
- Фикс (только touch-путь в main.ts, десктоп не тронут):
  1. тап, начавшийся внутри `#touchui` (`.tc-pad`/`.tc-look`/`.tc-act`), не
     открывает меню — контролы игровые, не «экран»;
  2. тап по фону **открытого** меню (вне `.panel`) его закрывает — тогл
     симметричен десктопному «~»; клик по фону мыши закрывает так же.
- Протокол/сервер не тронуты. §11 запись та же.

### 15.13 Латентность тач-движения: мгновенный flush инпута + рендер-буфер 66 мс (ревебр owner 2026-11-17)

- Ревебр owner (mobile playtest): «тап двигает только после отпускания — жёсткий
  input lag; снизить инертность раз в полтора». Инертности на сервере нет
  (`wish*speed*dt`, полная скорость в первом же тике, §9.3) — «движение после
  тапа» это сумма конвейера: цикл отправки input до 33 мс + тик сервера до
  33 мс + **буфер интерполяции рендера 100 мс** (инвариант ГДД) + one-way
  сеть. Короткий тап (150–250 мс) «отрабатывал» весь ход в буфере, и камера
  дёргалась уже после отпускания пальца.
- Фиксы (клиент, touch и desktop одинаково):
  1. **input-флеш при фактической смене контрольного состояния**: TouchOverlay
     вызывает callback при смене сектора стика (-1↔сектор, включая landing на
     сектор прямо с pointerdown; вход в мёртвую зону без смены сектора — не
     флешит) и на pointerup/ДЕЙСТВИЕ; Controls — на keydown/rising edge и

  4. точек входа на карте нет вовсе → порт прочего устройства в 2 м («дорогой
     вход», канал 6 с) — очередь владельца, была и до §15.14, сохранена.

### 15.18 Слайдеры настроек тача: фикс iOS user-select + отдельная зона тапа (ревебр owner)

- Ревебр owner: «слайдеры чувствительности прицела и размера контролов под
  мобилой не работают, а чекбокс инверсии работает». Первопричина не в wiring:
  `body.touch` носит `-webkit-user-select:none` (§15.3, чтобы палец не выделял
  текст), а WebKit/Safari при user-select:none ломает touch-drag бегунка
  `input[type=range]` — чекбоксу это не мешает (он на тапе), отсюда «галка
  живая, ползунки мёртвые». Фикс точечный: `input[type=range]` —
  `-webkit-user-select:auto`, на touch `touch-action:none` (бегунок тянется,
  скролла панели жестом по самому слайдеру не нужно) + увеличенный thumb
  (30px) и поле (32px) под палец. Десктоп не затронут.
- **Новый слайдер «ЗОНА ТАПА» 1.0×…1.8×** (`--tap`, localStorage
  `hs.tapScale`, только touch): хит-тест контролов шире самой картинки —
  `::after`-рамка вокруг `.tc-pad`/`.tc-look`/`.tc-act` с
  `inset:calc(50%*(1 - var(--tap)))` (при 1.5 это −25% с каждой стороны),
  radius наследуется. Картинка не меняется (в отличие от §15.16), события с
  рамки буллят в контрол: хит-тест стика нормализован по getBoundingClientRect
  ВИЗУАЛА и rad>1 трактует точку за кругом как штатную краевую зону захвата
  (§15.11), прицелу важны только дельты пальца, ДЕЙСТВИЕ — pointerdown.
  Пересечение с соседним контролом разрешает DOM-порядок (стик раньше
  прицела/кнопки — они поверх).
- Рядом: ползунок РАЗМЕР теперь тянется и в landscape-меню на iOS — тот же
  user-select-фикс.

### 15.21 Слайдеры настроек починены: причина была в snap-back, не в iOS

- Ревебр owner: «слайдеры вообще не работают, даже на десктопе» (после §15.18)
  и «посмотри историю, найди место где перестало работать». Бисект истории:
  регрессию внёс **f6ae181** (fix wiring order сенсы) — `reapplySens` объединила
  загрузку из localStorage и применение и вешалась на `input`: любое перетянутое
  значение мгновенно откатывалось к сохранённому. Симптом ровно «слайдер не
  двигается вообще» на всех платформах (стрелки клавиатуры и клик по треку —
  тоже input → тоже откат). Диагноз §15.18 «WebKit user-select» — ложный след:
  он не объяснял десктоп. Паттерн был тупо скопирован в новые reapplyCtl/
  reapplyTap (§15.16/15.18) — потому три слайдера «не работали» одинаково.
- **Фикс (hud.ts)**: load и apply разделены. `reapplySens/Ctl/Tap` (load+apply)
  — только на загрузке после wiring и на deploy; на `input` висят чистые
  `applySens/Ctl/Tap` (persist + live-эффект, без перечитки localStorage).
- **Тач-слой (hud.ts, только IS_TOUCH)**: на iOS Safari drag бегунка пальцем не
  поддерживается в принципе (только тап-переход по треку). `enableTouchDrag` —
  Pointer Events с `setPointerCapture`: pointerdown/pointermove ставят value по
  X-доле трека (квант по `step`) и шлют `input`. На десктоп-тач/Android работает
  вместе с нативным путем, на iOS — единственный drag.
- §15.18-правила (user-select:auto, touch-action:none, thumb 30px) оставлены:
  thumb под палец полезен, touch-action:none отдаёт жест слайдеру (pan-y
  оверлея съедал бы его), user-select:auto — безвредная страховка.

### 15.23 Центрированные надписи с letter-spacing съезжают влево — компенсация text-indent (ревебр owner)

- Ревебр owner (скрин splash): «выровняй надписи по центру, сейчас криво».
  Механика: `letter-spacing` CSS добавляет трек **и после последней буквы** —
  центрированная строка содержит невидимый «хвост» в один трек, поэтому
  видимые глифы уезжают влево на половину трека (логотип 14px — на 7px,
  «ЗАГРУЗКА РЕСУРСОВ» 5px — на 2.5px, «ИНИЦИАЛИЗАЦИЯ…» 1px — на 0.5px).
- Фикс v1: `text-indent`, равный `letter-spacing`, на центрированных текстах
  с треком: `.logo` (14px + оверрайды 7px), `.tag` (5px), `.panel .dim` (1px).
  Верно **только для вписывающейся строки**: хвостовой трек делает box на трек
  шире глифов, центрирование box'ом смещает глифы влево на ls/2; отступ
  первой строки = ls возвращает равенство сторон. `.setHead`/`#debug .dim` не
  тронуты (текст левый, хвост не мешает).
- **v2 (ревебр owner на v1: «стало ещё хуже», скрин с наездом на рамку)**:
  настоящая первопричина кривизны — **переполнение**. Панель splash фиксирована
  `min(420px, 92%)` → контент 352px, а HACKSTRIKE 42/14 = чернильные 393px:
  строка не влезает НИ ПРИ КАКОЙ ширине окна; на переполнении `text-align:
  center` не действует (строка прижата start'ом), а `text-indent` v1 ещё и
  сдвигал её вправо на 14px — отсюда «хуже» и наезд на рамку. Фикс:
  `.loadPanel { container-type: inline-size }` + `@container (max-width:470px)
  .logo { 28px/7px, indent 7px }` — компактный логотип (чернила 239px)
  влезает в панель сплэша и на десктопе, центрирование работает, indent
  доцентровывает хвостовой трек. Мобильный splash и desktop-splash теперь
  один макет (28/7). Старый Safari (<16, без @container) откатывается к v1-виду
  (не хуже). Замер v2 на живом стенде: @container применён (28px/7px/7px),
  CSS.supports container-type → true.
- `text-indent` остаётся верным средством хвостового трека; он НЕ лечит
  переполнение — перед компенсацией проверять, что строка влезает.

### 16.0. Срез и концепция: хайст как третий путь победы

Победа в матче — **гонка трёх условий**, побеждает первое исполненное:

1. **50 фрагов** команды (как раньше);
2. **10 минут** истекли → по счёту (как раньше);
3. **извлечение содержимого физического сейфа** — мгновенная победа
  (новое; macguffin = победа, решение владельца 2026-11-16 «финализируем»).

Два пути извлечения (обоим нужно сначала попасть в data-отсек — вход
только через код-замок d3, §16.7):

- **сила (CTF)**: унести PHYSAFE на базу → +10 фрагов → канал «вскрываем
  3 с» → победа. Пронести быстро не выйдет: в отсек всё равно надо попасть
  через код-замок d3 — код из сети или перебор с подсказками (любой класс,
  §16.7).
- **кибер (хайст)**: `door_key` (код d3, на SRV1) + `safe_key` (код сейфа,
  в NETSAFE) → cp + decrypt → ввести коды на месте → канал 3 с → победа.

Пасхалка топологии: код сейфа лежит в сетевом сейфе **внутри** запертого
отсека — удалённо достаётся, физически нет (курица-и-яйцо решается только
сетевым путём через сегмент s3).

Порядок гонки: фраг-кап (50) проверяется в момент начисления фрагов и
**раньше** извлечения — если +10 за доставку закрыли 50, матч кончается по
фрагам, канал извлечения аннулируется. «Заморозка» сейфа (враг перехватил
и держит/прячет у своей базы) — легальная защитная стратегия: третий путь
отнят, контрплей — зачистить базу и забрать (сейф роняется при смерти
носителя).

### 16.1. MEM и данные

- **PMEM удалён как сущность, RAM → MEM** (решение владельца 2026-11-16).
  MEM-размеры хостов (МБ, M5-константы):

| Хост | MEM | NB |
|---|---|---|
| дека хакера | 256 | оба ключа (180) влезают |
| SRV1/SRV2/SRV3 | 512 | decrypt-станции |
| терминал | 64 | door_key влезает, safe_key нет |
| камера | 32 | заготовка под будущие данные/chaff |
| switch | 16 | транзит крупного не стейджится |
| NETSAFE | 128 | хранит safe_key (120) |
| дверь / клапан | 8 | — |

- **Два независимых ресурса** (ревизия 1): слоты программ деки (§12.2, без
  изменений, `denied ram_full`) и MEM МБ — только для данных (`denied
  mem_full`): переименование RAM→MEM слотовую модель программ не трогает.
- **data item**: `{name, mb, enc, code?}` — осмысленные имена с иконками
  (решение владельца): `door_key` [60 МБ], `safe_key` [120 МБ]. Листинг
  данных хоста виден тому, кто затроянил хост (и себе — на деке всегда).
  После decrypt item становится `enc:false` и в листинге виден сам код
  (`code`) — владелец хоста получает его **без повторного decrypt**:
  перехват хоста = кража готового кода (решение владельца 2026-11-16).
- **Жизнь данных**: лежат в MEM хоста; mv переносит между MEM (item
  уходит из источника), cp копирует (§16.2 ревизия 3); **смерть хакера
  стирает MEM его деки** (данные
  деки умирают с ним); джек-аут НЕ стирает; **рестор сессии хранит
  инвентарь деки** (плейтест 2026-11-18 «хром»: session не хранил items —
  переподключение с новым id стирало данные деки); MEM чужих хостов от
  жизни хакера не зависит. **rm убивает навсегда** — никакого возрождения
  (решение владельца 2026-11-17, отклонил «бэкап с офсайта» как
  слишком игровой). Матч-киллер исключён не магией, а **двумя seed-копиями
  door_key** (t1 и t2, симметрия команд: снос своей копии вражеским
  хакером — контрится копией на чужой половине) и **физическим перебором
  d3** с подсказками (§16.7) — легитимная стратегия «удалил ключ → идём
  вскрывать замок руками» (решение владельца: «тоже прикольная»).
- **Перехват** (решение владельца «давай делать»): владелец хоста
  (последний trojan) видит и может стянуть (`data cp`) **чужие** данные
  из MEM хоста. Классика: расшифровал door_key на SRV — ушёл — враг перехватил
  SRV вместе с готовым кодом.

### 16.2. Данные: дек-шелл `data ls / cp / mv / rm / decrypt`

- Копирование: `run cp <src> <dst>`; перенос: `run mv <src> <dst>` —
  источник и приёмник под контролем (трояновый хост или дека), маршрут
  существует (чужой firewall исключает линк из маршрута, как в
  BFS-достижимости). Ревизия 3 (решение владельца 2026-11-18 «cp это
  КОПИРОВАНИЕ а не mv»): **cp — настоящая копия** (item остаётся и в
  источнике: MEM занят на обеих сторонах, копии множатся — chaff-игра
  сильнее, контрится rm), **mv — перенос** (прежняя семантика cp: item
  покидает источник). Время/канал/резервация приёмника — одинаково.
- Приёмнику нужен свободный MEM ≥ объёма — иначе `denied: mem_full`
  (тост «MEM ПРИЁМНИКА МАЛО»). **Резервация**: MEM резервируется на старте
  трансфера (memFree падает сразу) и освобождается при завершении/отмене —
  два трансфера не «проталкиваются» в один и тот же свободный объём.
- **Дубликаты запрещены**: item, уже лежащий на приёмнике (или летящий
  туда cp/mv), — `denied: dup` (no-op без занятия полосы). Копию можно
  удалить (`rm`, ниже): chaff = слить копии на хосты → rm → слить снова.
- **`rm`** — удаление данных с хоста: 0.5 с, только владелец хоста
  (trojan) или своя дека; wire `{"t":"run","prog":"rm","dev":"srv1",
  "data":"safe_key"}`.
- **`decrypt`** — подкоманда данных (§16.4): `data decrypt <key>[@host]`,
  reverse `door_key decrypt`, 🔓 в ls-строке дерева и инвентарях. Джоба —
  на хосте данных (нужен NPU), «либо прошло, либо нет», результат
  `enc:false` + код команде (HUD «КОД D3»).
- **UI — одна команда `data`** (ревизия 2, 2026-11-18, решение владельца:
  rsync-команда убрана **целиком**, имя придержано под будущую механику
  batch-вытаскивания нескольких ключей — §16.10; палитра/кнопки работают
  через шелл-команду `data` с подкомандами, wire-имена — `cp` (копия) и
  `mv` (перенос), ревизия 3):
  - `data ls [host]` — листинг хоста; **хост валиден и до, и после
    подкоманды** (`data ls t1` = `data t1 ls` — плейтест 2026-11-18: форма
    после подкоманды молча валилась в контекст); без аргумента —
    **контекст данных**: устройство активного таба → выбранная на карте
    цель → дека (плейтест: «жму data ls — а оно на деке, хотя T1
    затроянен» — у остального софта цель есть, у data не было). Явный
    хост-устройство в ls **переключает цель** (дальше софт 1–6 жал туда).
    Отказ доступа (чужой/нейтральный хост) — **красная строка** «ДОСТУП
    ЗАПРЕЩЁН — НУЖЕН TROJAN НА ЦЕЛИ» (плейтест: это ошибка, не подсказка).
    `deck` — адресуемое имя деки, алиас **`localhost`** (плейтест: «для
    деки надо алиас localhost ;)» — декиный sh-вайб; в кандидатах
    появляется только при явном вводе). Листинг — клиентский (scan-состояние), сервер не дёргается;
    данные видны только владельцу хоста (чужой/нейтральный → «НЕТ
    ДОСТУПА»). Результат рендерится **прямо в палитре** («терминал»,
    решение владельца из трёх вариантов): шапка хоста (MEM занято/ёмкость)
    + строки `key NМБ 🔒 [код]`; строки выбираемы (↑↓/тап) — Enter
    превращает строку ввода в `data <host> cp <key> ␣` (осталось указать
    приёмник); Esc/ввод — выход из листинга.
  - `data cp <key> [dst]` / `data mv <key> [dst]` — формы: `data cp key
    dst`, `data t1 cp key dst`, `t1 data cp key dst` (обратный порядок, как
    у программ). Источник: явный префикс-хост → активный таб (если там
    есть key) → дека → единственный свой хост с key; неоднозначно (ключ на
    нескольких хостах) — подсказка уточнить хостом. Приёмник без токена —
    дека (эксфильтрация).
  - `data rm <key>` — те же формы и резолюция источника.
  - **Обратная форма** (в контексте данных есть items): по слэшу первый
    кандидат — сам item (`door_key`, hint `@T1`/`@ДЕКА`), второй токен —
    `cp`/`mv`/`rm`, третий — приёмник.
  - Автодополнение по токенам: хосты (вкл. `deck`), подкоманды, ключи
    (только свои хосты/дека), приёмники (вкл. ДЕКА, владелец в hint).
  - **Анимированный cp-тост** (плейтест 2026-11-18: «давай анимацию в
    сообщении копирования»): вместо статичного тоста — карточка трансфера
    `CP KEY · SRC → DST` с полосой-бегущими-полосками (file-copy вайб),
    объём/скорость обновляются из deck-сообщения 2 Гц
    (`42 МБ · 20 МБ/С`); финиш — полоса добивается, «ГОТОВО ✓» (зелёная),
    гаснет через ~1.3 с; отмена (`denied cp_cancel`) и отказ операции
    (denied с prog/data, ред. 2026-11-18 «сам прогрессбар красным и
    мигающим — ой ой отказ») — красная карточка с мигающим красным баром
    («ОТКАЗ — ПРОГРЕСС ПОТЕРЯН» / причина из DENIED_TEXT), ~2.2–2.6 с.
    Карточка одна: отказ красит ТУ ЖЕ оптимистичную карточку (плейтест
    ревизии: «два прогрессбара — зелёный 100% и красный ниже»); карточка,
    ни разу не видевшая прогресс-тика, успешной быть не может — краснеет
    сама. Смерть/джек-аут — карточки
    умирают с сессией деки (трансферы сервер отменяет). Протокол не
    менялся — только клиент.
- **Кнопки деки**: ряд 1–6 прежний, вместо 7/8 — одна **`7 DATA`**
  (кнопка/хоткей 7): открывает палитру сразу с листингом активного таба
  (desktop) или деревом на уровне ДАННЫЕ (touch). Кнопки `→ ДЕКА`/`🗑 RM`
  в табе устройства и `🗑` в инвентаре деки — шорткаты, шлют те же `run`.
- **Touch-дерево** (§15.7): уровень устройства получает строку «ДАННЫЕ
  (n)» (видимые свои данные), корень — «ДЕКА: ДАННЫЕ (n)»; уровень items —
  строки с кнопками CP (→ уровень приёмника: ДЕКА + свои хосты) и 🗑 RM
  (сразу). Всё тапами, клавиатура не вызывается.
- **Отмена трансфера** (смена владельца src/dst, чужой firewall на линке
  маршрута, смерть/джек-аут оркестратора): прогресс теряется — «либо
  прошло, либо нет», симметрично decrypt. `denied: cp_cancel`.
- **Скорость = узкое место маршрута**: минимум по bw всех кабелей пути и
  backplane всех свитчей пути; конкурентные трансферы и сканы через те же
  линки делят полосу поровну (честные очереди на линках — сетевой аналог
  планировщика §5.1). Скорость трансфера = min его доли по всем линкам.
- **Роутинг**: widest-path (маршрут, максимизирующий узкое место; при
  равенстве — меньше хопов). Считается на старте трансфера, чужие
  firewall'ы исключают рёбра.

### 16.3. Пропускная способность сети (bw, МБ/с)

- Единица — **МБ/с везде** (ревизия 1): bw-модель оперирует только рёбрами
  графа устройств (кабели + радио-аплинки); входной хоп «дека ↔ точка
  входа» в модели не участвует, legacy-числа NET §12.2 (Мбит) не
  используются.
- Радио-аплинки пиннятся в карте явно (r1→s1, r2→s2), а не «к ближайшему
  свитчу» — добавление s4/s5/s6 не должно молча перекоммутировать сеть.
- **Спрос сканов**: portscan — 2 МБ/с на каждый линк своего текущего
  распространения; vulnscan/trojan — 4 МБ/с на линках пути к цели.
- Кабели: **магистраль 40 / доступ 20 / ветка 10 / радио 5**.
- Backplane свитчей: s1, s2, s6 = **60**; s4, s5 = **30**; **s3 = 20**
  (осознанное горлышко хранилища: всё, что за d3, делит одну шину).
- **Сканы едят канал наравне с cp-трансферами** (решение владельца «хорошее
  предложение»): portscan/vulnscan на загруженном линке замедляются своей
  долей. Отсюда: тяжёлый слив с NETSAFE замедляет вражеские сканы через
  ветку (видно, что «кто-то качает»), и наоборот — **chaff-слив** защитника
  насыщает собственный канал, вор качает дольше.
- Тайминги-ориентиры (чистый канал): door_key 60 МБ по доступу 20 = 3 с;
  safe_key 120 МБ по ветке 10 = **12 с** (событие, а не формальность).

### 16.4. decrypt

- Запуск: `run decrypt <data> @<host>` — джоба бежит **на хосте, где лежит
  данных**; хост обязан иметь NPU, иначе `denied: npu` (тост «НУЖЕН NPU»).
- Скорость: **дека 2 МБ/с (NPU ×1), SRV 6 МБ/с (NPU ×3)** →
  door_key: 30 с / 10 с; safe_key: 60 с / 20 с.
- **«Либо прошло, либо нет»** (решение владельца): частичных результатов
  нет — прерванная джоба = потерянное время; прогресс виден.
- Джоба **на SRV живёт на хосте**: переживает джек-аут и смерть
  запустившего; результат лежит в MEM SRV — может быть перехвачен (§16.1).
  Джоба **на деке** отменяется джек-аутом/смертью (как все процессы деки).
- Результат: item становится `enc:false` (код виден в листинге владельцу
  хоста — перехват = готовый код, §16.1) и **команда получает код навсегда**
  (HUD «КОД D3: 4731» / «КОД СЕЙФА: 8241»). Коды генерируются сервером на
  матч: 4 цифры, у d3 и сейфа разные.
- **Прогресс SRV-джобы виден команде** (ревизия 1): сообщение `job` 1 Гц
  (§16.9) — в том числе после джек-аута/смерти запустившего. Смена
  владельца SRV mid-job джобу НЕ отменяет — результат достанется новому
  владельцу хоста (перехват). NPU-очереди честные: две джобы на SRV =
  каждая ×0.5.
- Decrypt старт/финиш палевны как кибер-события: watcher'ы на хосте
  триггерятся (ev=install-аналог; в журнал пишется).

### 16.5. Серверы SRV1–SRV3 и встроенный щит ×3

- **SRV1**: 1 этаж, центральная комната [~32,1,33] (не у одного s1 —
  симметрия, решение владельца), **два кабеля по 20 на s1 и s2** (симметрия
  + ещё один цикл). Держит `door_key`. NPU ×3, MEM 512.
- **SRV2, SRV3**: машинный зал 2 этажа (§16.8), одинаковые (решение
  владельца «хорошая идея»): NPU ×3, MEM 512, без уникальных данных —
  резервные decrypt-станции у хранилища.
- **door_key — лут на время** (решение владельца 2026-11-18, «door_keyYYYYMMDDHHII»):
  одна копия на SRV1 (две seed-копии отклонены — «одна копия, так легче
  соревноваться»); ротация каждые **T = 120 с** по времени мира, имя =
  поколение `door_key<HHMM>_<YYYY-MM-DD>` (читаемо для игрока: часы-минуты
  генерации + дата — владелец: «HHII это часы и минуты, а не 1,2,3,4»), код d3 =
  4 знака FNV-1a от имени **и времени старта матча** (чистая дата иначе
  повторяла бы код между матчами одного дня).
  **Грейс**: код текущего и предыдущего поколения валиден (§16.7) — ротация
  за секунду до ввода не плевок в лицо. SRV1 держит ровно текущее +
  предыдущее поколение **кода**; сами ключи в MEM SRV1 копятся весь матч
  (решение владельца из плейтеста: max 6 поколений × 60 = 360 ≤ MEM 512 —
  «можно все 5 ключей за 10 минут сгенерить, хакер не будет знать какой
  валидный если srv1 не ломанул»; неоднозначность intentional). Копии на
  деках и SRV1 чистятся при старте нового матча (матч-специфичный лут не
  переезжает — это был настоящий баг). rm свежего ключа больше не
  матч-киллер: следующее поколение появится в ближайшую ротацию.
- **Встроенный щит ×3** (идея владельца «antivirus x3»): у каждого SRV при
  спавне 3 заряда (buildCyber: kind srv → shield=3). Каждая вражеская `vulnscan`/`trojan` попытка на SRV →
  `denied: shield` + −1 заряд (vulnscan не даёт vulnedBy — пробиваться
  надо гриндом: ~3 холостых + рабочий vulnscan + trojan ≈ 13–14 с).
  При 0 зарядов SRV взламывается как обычное устройство.
- Щит блокирует **любую** установку на чужой SRV (следствие решения (c)
  2026-11-16: watcher/firewall/antivirus на чужих/нейтральных требуют
  vulnscan, а vulnscan по щиту denied): **чужой SRV слеп для врага, пока
  щит жив** — ни разведки, ни софта. cp/decrypt/rm на ЗАХВАЧЕННОМ SRV
  идут свободно (своё — админишь без отмычки). После захвата владелец и
  его союзники щита не встречают; совместный гринд двумя хакерами одной
  команды — фича. Реген-таймер общий, от последнего отбоя.
- **Регенерация**: +1 заряд / 30 с (макс 3) — решение владельца 2026-11-16
  («ну давай 30с»): прожжённое отрастает, долбиться надо одним рывком.
- Попытки по щиту триггерят watcher'ы на SRV и пишутся в журнал (ev
  `shield`) — чужой watcher и есть способ узнать, что гринд начался.
- Игровой antivirus (§13.6) не трогается: щит — свойство серверного
  железа, не устанавливаемая программа.

### 16.6. Сейфы

- **NETSAFE**: data-отсек, у s3 [~29,8.2,33], ветка 10 МБ/с на s3, MEM 128,
  **без щита** (решение владельца: защита = дверь-код + лава lv3 +
  дистанционность). Обычное устройство: portscan → vulnscan → trojan →
  листинг → data cp safe_key.
- **PHYSAFE**: за лавой lv3 [~32,8.2,40.8 — вне бокса лавы, ревизия 1],
  **офлайн** (в графе сети его нет). Взять: space, любой класс, ×0.5
  скорости, отстреливаться можно, джек-ин нельзя, виден в снапе (поле
  `safe`, §9.2 — уже в протоколе). Смерть носителя → сейф падает на месте
  смерти (лежит, пока не подберут; F5-сессия: сейф остаётся на земле,
  каналы сбрасываются).
- **Извлечение — один раз за матч**: канал «вскрываем 3 с» (старт: у сейфа
  после ввода верного кода ИЛИ на базе после доставки), прерывается
  уроном. Успех → `matchend` с `reason:"extract"` (победа). Доставка на
  базу: **+10 фрагов один раз за матч** при первом старте канала (обрыв и
  рестарт не начисляют повторно — фикс ревизии 1: иначе FF-чип союзника
  превращал канал во фраг-ферму). Зона сдачи — радиус 6 м от точек спауна
  своей команды.
- Гейт лавы (осознанный, ревизия 1): у сейфа горит lv3, пока не закрыт
  клапан v3 — и ввод кода, и канал «вскрываем» стоят в огне (DoT прерывает
  канал): сперва погаси лаву (trojan-цепочка к v3 из сети).

### 16.7. Замок d3 (каталог §7 №4; решение владельца «только код»)

- Открывается **только**:
  1. **ввод кода** (4 знака, из door_key) — кем угодно из команды с кодом;
  2. **перебор с подсказками** (Fallout-style, решение владельца
     2026-11-16: «чтобы упоротый перебор работал с CTF-путём»; взлом на
     месте 200 с удалён — доминировался подсказками): любой класс у
     клавиатуры; серверный анти-флуд — не чаще одного `enter` в 2 с;
     на неверный код панель показывает **«N/4 цифр на месте»** (цифра
     верна и стоит на своей позиции). Реалистично ~60–120 с у двери —
     fallback для команды без хакера (открыл перебором → CTF-вынос
     сейфа), кибер-команда в ~3 раза быстрее (~35 с сети против стояния
     у двери). Неудачи пишутся в watcher-журнал d3, alert владельцу —
     агрегированный, не чаще 1 в 2 с; журнал ring-buffer 20 — спам-перебор
     выталкивает старые записи, брутфорс = способ замести следы:
     осознанная фича. Подсказки работают на **обеих** клавиатурах — d3
     и PHYSAFE (одна механика).
- **Удалённо — ничего**: ни trojan, ни vulnscan, ни ввод кода по сети.
  Троян на d3 управляет только створкой (open/close) **незапертой** двери;
  запереть/отпереть можно только кодом (ввод кода на открытой двери
  запирает её обратно).
- **Клавиатура-оверлей** (DOM, ред. 2026-11-18): d3 — обычная дверь для
  джек-ина (space у двери = jack-in, как у всех); рядом с каждой запертой
  дверью на стене — **маленькая клавиатура-пропс** (kind `keypad`, to=id
  двери): space у неё в радиусе 2 м → большая панель. Space у клавиатуры
  ПЕРЕХВАТЫВАЕТСЯ до джек-ина (клиент consume'ит interact), у самой двери —
  обычный джек-ин. Панель — 10 кнопок замка (1–9, C, 0, ⌫, ОТКРЫТЬ), по
  центру экрана, на уровне глаз; ввод — цифры с клавиатуры (слушаются на
  window: под pointer-lock фокуса полю не дать) и клик/тап.
  Сервер всегда отвечает: верный код — open/close (закрыл — снова замок),
  неверный — «N/4 цифр на месте» (цифра верна И на своей позиции; грейс:
  секрет — лучшее из двух поколений). Анти-флуд 1/2 с режет только
  журнал/alert, не ответ — панель не зависает на «ПРОВЕРКА…» (плейтест:
  «оно зависло на проверка»); у клиента страховочный таймаут.
  Прежняя спека «space на запертой двери → панель ввода» заменена.
  Верный код → дверь открывается; закрыл створку — снова заперта.
  Неверный → подсказка «N/4», запись в журнал, alert владельцу
  (агрегированно).
- Следствие топологии: t3 стоит **внутри** отсека — до открытия d3 весь
  сегмент s3 достижим только удалённо через стояки (физического входа в
  сетевой сегмент нет). Дверь, открытая врагом и не запертая обратно, —
  вход для всех (эмерджентный лаз, в т.ч. для безхакерной команды).

### 16.8. Карта: топология с циклами, машинный зал

Схема (bw: 40 магистраль / 20 доступ / 10 ветка / 5 радио):

```
════════════ 2-Й ЭТАЖ (терраса + машзал) ════════════
 МАШИННЫЙ ЗАЛ (новая комната у СВ-лестницы, вход — дверь d4 без кода):
    SRV2 [NPU×3, щит×3] ──20──┐
    SRV3 [NPU×3, щит×3] ──20──┤
                             [S6]═══40(c27, НОВЫЙ стояк)═══[S1] ↓ 1 этаж
                               │40(c28)
                              [S3] (backplane 20 — горлышко хранилища)
 data-отсек (за d3):           │
    NETSAFE [safe_key] ──10────┤
    PHYSAFE (офлайн, CTF)      ├──20── T3 (внутри!), CAM3, d3
    lv3 + valve3 «страж»       └──20── CAM4 (терраса)
                               40(c9, стояк) → [S2]
════════════ 1-Й ЭТАЖ ════════════
 [S2]════════40════════[S1]              ← магистральное кольцо
 R2~~~5~~~S2         S1~~~5~~~R1         ← радио-аплинки
 [S5 восток]──40──S2   S1──40──[S4 запад] ← новые свитчи
 S5 ───────40──────S1   S4─────40─────S2  ← двойные аплинки = циклы
 SRV1 [door_key, NPU, щит×3] — центр [~32,1,33], ДВА кабеля 20 на s1+s2
 T1/CAM1/D1 — на s4 (запад)      T2/CAM2/D2/G1 — на s5 (восток)
 БАЗЫ = респаун-зоны зап/вост — точка сдачи PHYSAFE
```

- **Итог** (ревизия 1): свитчей 6 (s1–s3 + s4, s5, s6 в машзале),
  серверов 3, сейфа 2; кабелей 17 существующих + 11 новых = **28** + 2
  радио-аплинка: **c27** s1–s6, **c28** s6–s3, **c29/c30** s4–s1/s2,
  **c31/c32** s5–s1/s2, **c33/c34** SRV1–s1/s2, **c35/c36** SRV2/SRV3–s6,
  **c37** NETSAFE–s3. Нумерация c27+ — c15/c16/c17 уже заняты кабелями
  клапанов v1/v2/v3; существующий c3 s1–s2 разметить магистралью 40, не
  дублировать. Перекоммутация конечных устройств 1 этажа на s4/s5
  (T1/CAM1/D1 → s4, T2/CAM2/D2/G1 → s5) — карт-итерация 8.
- **Второй стояк проходит ЧЕРЕЗ машинный зал** (s1→s6→s3, решение
  владельца): зал — транзитный узел половины трафика 2 этажа, за него
  бьются по двум причинам (NPU + маршрут).
- **Машзал**: новая комната 2 этажа у СВ-лестницы; точная геометрия и
  координаты — на картографической итерации (§16.10, итерация 7).
- **Лестницы шире и положе** (по ним несут PHYSAFE ×0.5 — решение
  владельца), **потолки ниже** (решение владельца; аккуратно: камеры
  висят на этаж+1.6, коллизии, клим-тесты §14.6 не сломать).
- Известный дисплей-кворк: клапан v3 (y=14.1, под крышей над data-отсеком)
  попадает в ярус «Э3» карты деки (порог y<11, §13.3.1) — третьего этажа
  нет, это высота подвеса пропа. На карт-итерации: полосить по плите этажа
  или опустить визуал клапана.

### 16.9. Протокол M5 (добавление к §9.2/§12.5/§13.2)

C→S:
```jsonc
{"t":"run","prog":"cp","dev":"netsafe","dst":"deck"}      // src=dev, dst=deck|hostId
{"t":"run","prog":"decrypt","dev":"srv1","data":"door_key"}  // джоба на dev (нужен NPU), данные лежат там же
{"t":"run","prog":"rm","dev":"srv1","data":"safe_key"}        // удалить данные с хоста (владелец trojan / дека)
{"t":"enter","dev":"d3","code":"4731"}                        // ввод кода на клавиатуре (физически у двери; анти-флуд 1/2 с)
```
S→C:
```jsonc
{"t":"scan","devices":[{"id":"netsafe","kind":"safe","mem":128,"memFree":8,
  "net":[{"id":"s3","mbps":10},{"id":"d3","mbps":20}],"bp":0,
  "data":[{"n":"safe_key","mb":120,"enc":true}],"owner":7,...}]}
                                        // net[] (M5, итерация 1.5): bw каждого линка устройства
                                        // (кабель или радио-аплинк), МБ/с — для UI табов и ширины
                                        // линий карты; bp (omitempty) — backplane свитча.
                                        // data[] — только если хост мой (trojan) или это дека
{"t":"deck","memUsed":180,"data":[{"n":"safe_key","mb":120,"enc":false,"code":"8241"}],
 "progs":[...,{"id":9,"prog":"cp","dev":"netsafe","dst":"deck",
  "mbLeft":84,"mbps":10},...]}          // инвентарь деки + прогресс трансфера (ревизия 1)
{"t":"job","dev":"srv1","data":"door_key","prog":0.62}
                                        // 1 Гц, команде владельца джобы: прогресс SRV-decrypt,
                                        // в т.ч. после джек-аута/смерти запустившего (ревизия 1)
{"t":"denied","reason":"mem_full|dup|npu|shield|locked","dev":"srv1"}
{"t":"keypad","dev":"d3"}                // у запертой двери: открыть оверлей ввода
{"t":"code","dev":"d3","ok":true,"open":true}  // результат ввода; ok=false — неверный код, match=N — подсказка «N/4»; open (omitempty) — итоговое состояние створки: код-ТОГГЛ, повторный ввод ЗАКРЫВАЕТ и запирает (плейтест «пишет ОТКРЫТО, а дверь закрывается» — клиент отвечает «ПРАВИЛЬНО»); неверный код на открытой двери отвечает N/4, не ok=true
{"t":"codes","door":"4731","safe":"8241"} // команде, по мере узнавания (поля omitempty)
{"t":"extract","team":1,"by":7,"stage":"channel"}  // broadcast: канал «вскрываем» начат
{"t":"extract","team":1,"stage":"win"}             // → следом matchend reason=extract
{"t":"matchend","winner":1,"scores":[24,31],"reason":"frags|time|extract"}
```
`snap.props[]` += `netsafe` (kind safe, владение как у устройств) и
`physafe` (kind physafe, pos; когда несут — поле `carriedBy`, pos
дублирует позицию носителя). Поле игрока `safe` (несёт PHYSAFE) уже есть
в §9.2. watcher-события (ревизия 1, расширение enum §13.2):
`shield` (отбой щитом), `job` (старт/финиш decrypt/cp на устройстве),
`codefail` (неверный код d3) — в
`alert.ev`/`scan.devices[].log`. Поля `mem/memFree` в scan видимы всем,
кто открыл устройство; `data[]`/заряды щита SRV — только владельцу
(trojan).

### 16.10. Итерации (один объект за итерацию, плейтест после каждой)

1. **Канал сети**: таблица bw для ВСЕХ существующих кабелей c1–c17,
   backplane свитчей, честные очереди на линках, widest-path, спрос
   сканов (2/4 МБ/с), сканы делят канал (без новой геометрии).
   Чекпоинт: весь старый e2e (m2_smoke 7/7, e2e_smoke) зелёный — тайминги
   сканов меняются только под нагрузкой канала.
2. **MEM + rsync + rm** ✅ (2026-11-17): data-модель (`{n,mb,enc,code?}`),
   MEM-ёмкости по типам хостов (дека 256 / srv 512 / терминал+радио 64 /
   камера 32 / switch 16 / safe 128 / дверь-клапан-газ 8), резервация MEM на
