## Оптимальный стек для P2P браузерной игры

### 1. **Сетевой слой: Trystero** (TypeScript/JavaScript)
Это лучшая готовая библиотека для P2P в браузере:
- Работает через **WebRTC** (прямое соединение между игроками)
- Поддерживает разные бэкенды для обнаружения пиров: BitTorrent, IPFS, Firebase, Nostr
- Не требует серверной части (только signaling через публичные сервисы)
- Простой API: `joinRoom()`, `sendAction()`, `onAction()`
- Активно развивается, есть примеры игр

### 2. **Синхронизация состояния: Y.js или Automerge** (TypeScript)
Для P2P игр критична синхронизация без конфликтов:
- **Y.js** — CRDT библиотека, идеально подходит для синхронизации игрового состояния
- Автоматически разрешает конфликты, когда два игрока одновременно меняют одно и то же
- Работает поверх WebRTC через Trystero
- Легковесная, быстрая

### 3. **Рендеринг: Three.js или Babylon.js** (TypeScript)
- **Three.js** — самый популярный, огромное сообщество, много примеров
- **Babylon.js** — более "игровой" движок с встроенной физикой, коллизиями
- Оба отлично работают с TypeScript
- Экспорт в WASM не нужен — JavaScript достаточно производительен для большинства игр

## Почему НЕ WASM+WebGPU?

**WASM+WebGPU** — это избыточно для P2P игры:
- WebGPU нужен только для сложной 3D графики (тысячи объектов, шейдеры)
- WASM усложняет разработку — нужно писать на Rust/C++ и компилировать
- Для FPS-шутера достаточно Three.js/Babylon.js
- WebRTC и CRDT библиотеки уже написаны на JavaScript/TypeScript

## Почему НЕ Protos Engine?

**Protos Engine** — это не стандартный выбор для P2P игр:
- Я не нашел информации о нем как о специализированном P2P движке
- Если это какой-то нишевый движок, у него будет меньше документации и сообщества
- Проще собрать стек из проверенных компонентов (Trystero + Y.js + Three.js)

## Конкретная рекомендация для вашего FPS-шутера

Учитывая, что вы хотите сделать игру с механикой "хакера с декой" (из предыдущего контекста), вот оптимальный стек:

```typescript
// Стек для P2P FPS игры в браузере
- Trystero (P2P связь через WebRTC)
- Y.js (синхронизация состояния: позиции игроков, здоровье, взломанные устройства)
- Three.js или Babylon.js (рендеринг 3D мира)
- Cannon.js или Ammo.js (физика, если нужна)
- TypeScript (вся логика игры)
```

**Преимущества этого стека:**
- Полностью P2P, без серверов
- Работает в любом современном браузере
- TypeScript дает типобезопасность
- Легко модифицировать и расширять
- Большое сообщество и документация

## Почему нет готовых решений?

1. **P2P в браузере сложно для FPS** — синхронизация позиций, стрельбы и попаданий требует точной сетевой модели, а в P2P без сервера сложно реализовать античит и разрешение конфликтов
2. **Trystero — молодая библиотека** (появилась в 2022), под неё ещё не написано крупных игр
3. **Большинство браузерных шутеров используют серверную часть** (Socket.io, Colyseus, PlayFab) для надёжности

## Что делать?

Если вы хотите именно **командный P2P шутер в браузере**, у вас два пути:

### Путь 1: Собрать свой стек (рекомендую)
Использовать Trystero + Y.js + Three.js, но начать с простого прототипа:
1. Взять базовый FPS-шаблон на Three.js
2. Добавить Trystero для P2P-соединения
3. Использовать Y.js для синхронизации позиций игроков
4. Постепенно добавлять командную логику, оружие, взлом устройств

Это займёт время, но даст полный контроль.

### Путь 2: Использовать готовый движок с P2P поддержкой
- **PlayCanvas** — есть примеры мультиплеера
- **Babylon.js** — имеет сетевые примеры, но чаще с сервером
- **Colyseus** — фреймворк для мультиплеера (но требует сервер)

### Путь 3: Гибридный подход
Использовать Trystero для P2P, но добавить **минимальный signaling-сервер** (например, на Firebase или PeerJS Cloud) для обнаружения пиров. Это не полноценный игровой сервер, но решает проблему NAT traversal.

### USER
для Xonotic и Unvanquished можно ли пробросить серверную часть через ngrok чтобы игроки просто ввели адрес?

### ASSISTANT
Коротко: **через ngrok — нет.** И Xonotic, и Unvanquished работают по **UDP**, а ngrok туннелирует только HTTP/TCP. Но задача «игроки просто вводят адрес» решается другими туннелями — ниже рабочие варианты.

---

## Почему ngrok не подходит

| Игра | Движок | Транспорт | Порт по умолчанию |
|---|---|---|---|
| Xonotic | DarkPlaces (Quake-derived) | **UDP** | `26000/udp` |
| Unvanquished | Daemon (ioquake3-derived) | **UDP** | `27960/udp` |

Quake-подобный неткод — это сырые UDP-датаграммы со своим слоем надёжности поверх. TCP-туннель их просто не примет: клиент отправит UDP-пакет в никуда.

Теоретически можно собрать костыль `socat UDP↔TCP` на сервере → ngrok TCP → `socat TCP↔UDP` **на машине каждого игрока**. Но это (а) ломает «просто ввели адрес», (б) даёт head-of-line blocking: одна потерянная пачка → фризы у всех. Для arena-FPS это смерть. Не делайте так.

---

## Что реально работает

| Вариант | UDP | Свой сервер | Игроки вводят адрес | Цена |
|---|---|---|---|---|
| **playit.gg** | ✅ | не нужен | `abc.playit.gg:54321` | free |
| **frp + VPS** | ✅ | нужен VPS | `vps.example:26000` | ~$3–5/мес |

| **Игра прямо на VPS** | ✅ | нужен VPS | `vps.example:26000` | ~$3–5/мес |
| Tailscale / WireGuard | ✅ | — | ❌ клиент у каждого | free |
| Cloudflare Tunnel / Tailscale Funnel | ❌ | — | — | — |

## Вариант 1: playit.gg — ближе всего к «ngrok для игр»

Бесплатный агент, заточенный под игровые серверы, UDP из коробки.

```bash
# нативный arm64-агент с playit.gg (в Docker на macOS смысла нет —
# агенту нужен доступ к 127.0.0.1 хоста)
./playit
```

В веб-панели создаёте туннель: тип **UDP** (или TCP+UDP), local port `26000` для Xonotic / `27960` для Unvanquished. Получаете адрес вида `xyz.playit.gg:54321` — его и раздаёте.

Подключение:
```
# Xonotic — консоль
connect xyz.playit.gg:54321

# Unvanquished — консоль
/connect xyz.playit.gg:54321
```

Минусы free-тарифа: релеи могут быть далеко (пинг +30–80 мс), IP общий, порт случайный. Свой домен можно навесить CNAME, **но порт всё равно придётся указывать** — SRV-записи эти движки не понимают.

## Вариант 2: frp + VPS — предсказуемо и под вашим контролем

Учитывая, что вы живёте в CLI и Docker Compose — это ваш вариант.

**На VPS (`frps.toml`):**
```toml
bindPort = 7000
auth.method = "token"
auth.token = "длинный_секрет"
```

**На маке (`frpc.toml`):**
```toml
serverAddr = "VPS_IP"
serverPort = 7000
auth.method = "token"
auth.token = "длинный_секрет"

[[proxies]]
name = "xonotic"
type = "udp"
localIP = "127.0.0.1"
localPort = 26000
remotePort = 26000

[[proxies]]
name = "unvanquished"
type = "udp"
localIP = "127.0.0.1"
localPort = 27960
remotePort = 27960
```

```bash
brew install frp
frps -c frps.toml   # на VPS
frpc -c frpc.toml   # локально
```

Игроки вводят `VPS_IP:26000` — порт нормальный, адрес стабильный, можно повесить A-запись на свой домен. Не забудьте открыть UDP-порты в firewall VPS.

## Вариант 3 (самый здравый для прода): сервер прямо на VPS

Xonotic и Unvanquished dedicated — очень лёгкие: пара сотен МБ RAM, минимум CPU. Двухъядерный VPS за $5 держит 8–16 игроков без туннелей вообще. Туннель домой через M4 Max имеет смысл только для дев-итераций (быстро пересобрал карту/скрипт — показал друзьям), а постоянный паблик лучше держать на VPS.

Плюс на Apple Silicon есть нюанс: macOS-сборки Xonotic исторически x86_64 → Rosetta. Linux-dedicated в контейнере через OrbStack часто оказывается проще и стабильнее нативного бинарника.

---

## Нюансы, о которые спотыкаются

- **CGNAT.** Если `ip addr` на роутере показывает `100.64.x.x` / `10.x.x.x` — обычный проброс не заработает, только туннель.
- **Мастер-сервер.** При туннеле сервер анонсирует наружу не тот адрес, что видят игроки. Отключите публичный анонс (в Xonotic — `sv_public 0`) и раздавайте адрес вручную, иначе люди будут кликать нерабочую строку в браузере серверов.
- **RCON.** Обязательно `rcon_password` посложнее + не публикуйте rcon-порт в туннеле. Открытый UDP-игровой порт без rcon — норм, с дефолтным паролем — вас снесут за вечер.
- **Задержка.** Xonotic и Unvanquished умеют client-side prediction и lag compensation, так что +40 мс от релея играбельны для казуала, но для дуэлей на скилле — уже нет. Выбирайте ближайший регион релея/VPS.

---

**Итого:** ngrok отпадает из-за UDP. Хотите «как ngrok, но работает» — **playit.gg**, бесплатно и за пять минут. Хотите стабильный адрес и контроль — **frp на дешёвом VPS**. Хотите постоянный паблик-сервер — крутите сам сервер на том же VPS и вообще забудьте про туннели.

## 1. Скачать бинарник под Apple Silicon

Официальный агент лежит в релизах `playit-cloud/playit-agent`. Сначала посмотрите актуальные имена ассетов (они меняются между версиями):

```bash
curl -s https://api.github.com/repos/playit-cloud/playit-agent/releases/latest \
  | grep -o '"browser_download_url": *"[^"]*"' | cut -d'"' -f4
```

Из списка берёте тот, где есть `darwin`/`macos` **и** `aarch64`/`arm64` (M4 Max — не x86_64):

```bash
mkdir -p ~/.local/bin
curl -L -o ~/.local/bin/playit "<URL_из_списка>"
chmod +x ~/.local/bin/playit

# если качали через браузер, а не curl — снять карантин Gatekeeper
xattr -dr com.apple.quarantine ~/.local/bin/playit 2>/dev/null || true

export PATH="$HOME/.local/bin:$PATH"   # добавить в ~/.zshrc
```

Homebrew-формулы в core может не оказаться — проверьте `brew search playit`, но путь через бинарник работает всегда и не тянет зависимостей.

## 2. Привязать агент к аккаунту

```bash
playit
```

При первом запуске агент напечатает claim-ссылку вида `https://playit.gg/claim/xxxxx`. Открываете в браузере, логинитесь (GitHub/Google/Discord), подтверждаете — агент привязан и покажет TUI со статусом. Секрет он сохраняет локально, повторный claim не нужен.

## 3. Создать туннель

Дашборд playit.gg → **Tunnels** → **Add Tunnel**:

| Параметр | Xonotic | Unvanquished |
|---|---|---|
| Тип | UDP (или TCP+UDP) | UDP |
| Local address | `127.0.0.1` | `127.0.0.1` |
| Local port | `26000` | `27960` |
| Region | ближайший к игрокам | то же |

Получаете публичный адрес вида `xyz.playit.gg:54321` — его и раздаёте.

## 4. Проверка

Поднимаете dedicated-сервер, потом в клиенте:

```
# Xonotic — консоль
connect xyz.playit.gg:54321

# Unvanquished — консоль
/connect xyz.playit.gg:54321
```

В дашборде у туннеля должен гореть онлайн-статус, а в логе агента — трафик. Если статус есть, а коннекта нет — почти всегда неверный тип туннеля (TCP вместо UDP) или сервер слушает не тот порт.

## 5. Автозапуск

**Для дев-итераций** проще всего tmux:

```bash
tmux new -s playit -d 'playit'
tmux attach -t playit
```

**Постоянно** — LaunchAgent. `~/Library/LaunchAgents/gg.playit.agent.plist`:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN"
  "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
  <key>Label</key><string>gg.playit.agent</string>
  <key>ProgramArguments</key>
  <array>
    <string>/Users/ВАШ_ЮЗЕР/.local/bin/playit</string>
  </array>
  <key>RunAtLoad</key><true/>
  <key>KeepAlive</key><true/>
  <key>StandardOutPath</key><string>/tmp/playit.log</string>
  <key>StandardErrorPath</key><string>/tmp/playit.err</string>
</dict>
</plist>
```

```bash
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/gg.playit.agent.plist
launchctl kickstart -k gui/$(id -u)/gg.playit.agent
tail -f /tmp/playit.log

# снять с автозапуска
launchctl bootout gui/$(id -u)/gg.playit.agent
```

Агент при отсутствии TTY обычно сам переходит в обычный лог-режим; если упрётся в интерактивный интерфейс — гляньте `playit --help`, там есть флаг отключения TUI.

## Нюансы именно вашей конфигурации

**Сервер в Docker/OrbStack.** Агент ставьте **нативно на macOS**, не в контейнер. Порты контейнера публикуйте на хост:

```yaml
ports:
  - "26000:26000/udp"
```

Тогда `127.0.0.1:26000` в настройках туннеля доедет до контейнера. Если всё же захотите агент в контейнере (`ghcr.io/playit-cloud/playit-agent`, привязка через `-e SECRET_KEY=...`), то в дашборде в качестве local address надо указывать `host.docker.internal`, а не `127.0.0.1` — иначе агент будет стучаться сам в себя.

**Прочее:**
- macOS-фаервол исходящие не режет, отдельно разрешать агенту ничего не нужно.
- Не забудьте `rcon_password` и `sv_public 0` в конфиге сервера — публичный анонс через туннель отдаст нерабочий адрес в браузер серверов.
- Free-тариф даёт общий IP и случайный порт: свой домен можно навесить CNAME, но порт в адресе всё равно останется — SRV эти движки не читают.
